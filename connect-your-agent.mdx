## Overview

This documentation site publishes a **documentation MCP server** at `https://docs.bridge.new/mcp`. Connect it to your AI coding assistant to search these pages and read the published API schemas, webhook events, and error references.

The server is public and needs no Bridge API Key. Its search and reading tools access documentation only. A separate, optional feedback tool sends comments about the documentation to the Bridge team.

<Warning>
  **This server reads documentation. It does not call the Bridge API.**

  It cannot create a contact, send a message, or read your workspace data. Calling the REST Integrations API requires your own code and an API Key — see [Authentication](/credentials). The public [Lead Capture](/lead-capture) endpoint uses its own setup and does not take an API Key.
</Warning>

## Connect your client

<Tabs>
  <Tab title="Claude Code">
    Run:

    ```bash
    claude mcp add --transport http bridge-docs https://docs.bridge.new/mcp
    ```

    Verify the connection with `claude mcp list`.
  </Tab>

  <Tab title="Cursor">
    1. Press <kbd>Command</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd> (<kbd>Ctrl</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd> on Windows) to open the command palette.
    2. Search for `Open MCP settings`.
    3. Click **Add custom MCP** to open `mcp.json`.
    4. Add the server:

    ```json
    {
      "mcpServers": {
        "bridge-docs": {
          "url": "https://docs.bridge.new/mcp"
        }
      }
    }
    ```
  </Tab>

  <Tab title="Codex">
    In `~/.codex/config.toml`, add:

    ```toml
    [mcp_servers.bridge-docs]
    url = "https://docs.bridge.new/mcp"
    ```
  </Tab>

  <Tab title="VS Code">
    Create a `.vscode/mcp.json` file in your project and add:

    ```json
    {
      "servers": {
        "bridge-docs": {
          "type": "http",
          "url": "https://docs.bridge.new/mcp"
        }
      }
    }
    ```
  </Tab>

  <Tab title="Claude">
    1. Go to the [Connectors](https://claude.ai/settings/connectors) page in your Claude settings.
    2. Click **Add custom connector**.
    3. Enter `bridge-docs` as the name and `https://docs.bridge.new/mcp` as the URL.
    4. Click **Add**.
    5. In a conversation, click the attachments button and select the server.
  </Tab>
</Tabs>

## What your assistant can do

Once connected, your assistant has three tools:

| Tool | What it does |
| :--- | :--- |
| **Search documentation** | Finds relevant pages and API definitions, with links to the source. |
| **Query documentation filesystem** | Reads complete pages and OpenAPI specs in a virtual filesystem containing this site's documentation. It does not run commands on your computer. |
| **Submit feedback** | Optionally sends a comment about an incorrect, outdated, or incomplete page to the Bridge documentation team. |

Ask your assistant to check the published contract before writing integration code. Search finds the relevant sources; reading the endpoint or schema supplies the exact fields.

---

## Read the contract before generating code

Use the [documentation index](/llms.txt) to find pages. The [collected documentation](/llms-full.txt) brings guides and endpoint descriptions together, but does **not** embed every request and response schema.

Before generating code, read the relevant contract:

- [REST Integrations OpenAPI](/api-reference/openapi.yaml) — REST methods, paths, authentication, parameters, request bodies, and responses.
- [Lead Capture OpenAPI](/api-reference/campaign-leads.openapi.yaml) — the separate public Lead Capture endpoint.
- [Webhook guides](/webhooks) — configuration, event payloads, and verification.

You can also append `.md` to an endpoint's documentation URL to read its Markdown page and embedded OpenAPI definition. Through MCP, use **Query documentation filesystem** to read the relevant page or schema.

Keep the published method, path, header and field names, types, required fields, enums, defaults, limits, and response codes exactly as documented. Do not invent fields or treat similarly named identifiers as interchangeable.

If two published sources disagree, identify the conflicting passages and ask Bridge support to confirm the behavior before relying on it. Do not resolve a contradiction by guessing or changing a signature.

## Example questions

Ask your assistant these in a project where you are integrating with Bridge:

- Which header does the Bridge API use for authentication, and against which host?
- Write a Python function that creates a contact in Bridge, using the required fields from the API reference.
- Which webhook events does Bridge emit when a conversation changes, and what does each payload contain?
- How do I verify the signature on an incoming Bridge webhook?
- What does Bridge error code `BRIDGE_CONVERSATION_0001` mean?

## Scope and availability

<Note>
  The server returns what is published on this site. Pages that are not part of this site's navigation are not indexed and cannot be retrieved.
</Note>

The server is hosted by our documentation provider as part of this site. Treat it as best-effort: it has no separate uptime commitment, and it applies rate limits well above normal use. If a request fails, read the pages directly.

If your assistant's answer conflicts with a published schema, check the linked endpoint and schema before using the code. If the documentation itself is inconsistent or incomplete, contact [support@sainapsis.com](mailto:support@sainapsis.com) or use the optional feedback tool.
