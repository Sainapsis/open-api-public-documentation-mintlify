# REST API authentication

Source: https://docs.bridge.new/credentials

Generate and use a server-side API key for the REST Integrations API, and keep it separate from webhook credentials and Custom Connections.

## Overview

Every request to the **REST Integrations API** at `https://api-connect-us.bridge.new` uses an **API Key** in the `x-api-key` header. This key identifies your application and authorizes it to access Bridge resources on behalf of your organization.

| Integration surface | Credential handling |
| --- | --- |
| REST Integrations API | Server-side `x-api-key` sent to `https://api-connect-us.bridge.new`. |
| Webhooks | Your receiver checks the configured webhook API key, HMAC signature and freshness policy. Follow [Verify signatures](https://docs.bridge.new/webhooks/verifying-signatures.md). |
| Custom Connections | Browser-side public `captureKey` and reCAPTCHA; no authentication header. Follow its [integration guide](https://docs.bridge.new/lead-capture/integration.md). |

**Note**

  You will need access to Bridge's admin console at https://admin.bridge.new.

  If you don't have one, please ask your Bridge Admin to create you a user.

---

## Generating an API Key

  

### Open the Admin Console

    Go to your [Bridge Dashboard](https://admin.bridge.new) and log in with your credentials.
  

  

### Navigate to API Keys

    In the left panel, go to **Developers → API Keys Management**.
  

  

### Create a new key

    Click **Generate New Key**. You can give it a descriptive name and set an expiration date.

    

**Warning**

      **Important:**\
      Your API Key will only be displayed once upon creation. Copy it immediately and store it in a secure location — you will not be able to retrieve it later.
    

  

---

## Using your API Key

Include your REST API Key in the `x-api-key` header on every request to the REST Integrations host:

```bash
curl -X GET "https://api-connect-us.bridge.new/bridge/api/health" \
  -H "x-api-key: YOUR_API_KEY"
```

```javascript
const response = await fetch("https://api-connect-us.bridge.new/bridge/api/health", {
  method: "GET",
  headers: {
    "x-api-key": "YOUR_API_KEY",
  },
});

const data = await response.json();
console.log(data);
```

```python
import requests

response = requests.get(
    "https://api-connect-us.bridge.new/bridge/api/health",
    headers={"x-api-key": "YOUR_API_KEY"}
)

print(response.json())
```


**Note**

  Use the `GET /bridge/api/health` endpoint to verify that your API Key is valid and your connection is working correctly.

---

## Security Best Practices

- **Use environment variables** — Store your API Key in an environment variable (e.g. `BRIDGE_API_KEY`) instead of hardcoding it in your source code.
- **Never expose keys in client-side code** — API Keys should only be used in server-side applications. Never include them in frontend code, mobile apps, or public repositories.
- **Set an expiration date** — Always configure an expiration when creating a key. Avoid using keys without a defined expiry.
- **One key per application** — Use a separate API Key for each service or application that connects to Bridge. This limits the impact if a key is compromised.
- **Rotate keys periodically** — Create a new key and update your applications before deactivating the old one. This ensures zero downtime during rotation.

## Troubleshooting

| Error | Possible Cause | Solution |
| ----- | -------------- | -------- |
| `401 Unauthorized` | Invalid, expired, or missing API Key | Verify that your key is correct, active, and included in the `x-api-key` header |
| `403 Forbidden` | The API Key does not have access to the requested resource | Check that your key has the necessary permissions for this endpoint |
| Cannot retrieve API Key | The key is only shown once at creation time | Generate a new API Key from the Admin Console |

For a complete list of error codes, see the [Error Codes](https://docs.bridge.new/error-codes.md) reference.

# Glossary and identifiers

Source: https://docs.bridge.new/guides/identifiers

Find the correct workspace, Contact, Bridge User, Agent, conversation, template, line, and media identifiers without confusing them.

## Start with the right integration

The **REST Integrations API** reads or changes workspace resources from your server using `x-api-key`. **Webhooks** send events from Bridge to your receiver. **Custom Connections** registers leads from a landing page using its separate public endpoint, `captureKey`, and reCAPTCHA.

An API Key is a server-side secret. A Custom Connections `captureKey` is designed to be in the landing page. These values are not interchangeable. See [Authentication](https://docs.bridge.new/credentials.md) and [Custom Connections](https://docs.bridge.new/lead-capture/index.md).

## People, Agents, and lines

- A **Contact** is the external person your business communicates with. Contact endpoints and external conversation participants refer to this person.
- A **Bridge User** is an internal human user. Internal-user lookup and handoff assignees refer to these users.
- An **Agent** is an automated Agent exposed by the Agents API. Its type is `LEADSCOUT` or `SERVICE_AGENT`; it has its own identifier, availability, and lines.
- A **provider** is a channel type, such as `WHATSAPP`. A **line** is a specific channel used for a conversation. A provider type, phone number, and `providerChannelId` are different values.
- A **workspace** scopes the request. A **brand** is another identifier used where the operation requires or accepts it; it is not a workspace or a line.

A Contact's `ownerId` refers to a Bridge User, not an automated Agent. Resolve it with the [internal-user read endpoint](https://docs.bridge.new/api-reference/internal-users-api/retrieve-an-internal-user-by-id.md).

## Where each identifier comes from

Use identifiers from the intended workspace. Do not reuse an identifier merely because the same phone number, email, or name appears in another workspace.

| Value you need | Where to obtain or verify it | What to pass |
| --- | --- | --- |
| `workspaceId` | Use the workspace identifier supplied for your integration. If it is missing, ask your Bridge administrator. The published REST contract does not provide a global workspace-list endpoint. | The workspace ID in the operation's path. Custom Connections also requires it in its body and, for browser requests, query string. |
| Contact ID | [Look up a Contact](https://docs.bridge.new/api-reference/contacts-api/retrieve-a-contact-by-an-identifier.md) by `PHONE`, `EMAIL`, or `ID`; list, create, and upsert responses also return the Contact's `id`. | The returned `id` for `{contactId}` or an identifier object with `identifierType: "ID"`, where that operation accepts it. |
| Bridge User ID | [Look up an internal user](https://docs.bridge.new/api-reference/internal-users-api/retrieve-an-internal-user-by-an-identifier.md) by `EMAIL` or `ID`, or use the internal-user list. | The returned `id` for `{userId}` or an internal identifier object. Internal-user lookup does not accept `PHONE`. |
| Agent ID | [List Agents](https://docs.bridge.new/api-reference/agents-api/list-the-agents-of-a-workspace.md). Read `agents[].id`, `type`, and `available`. | `agents[].id` for `{agentId}` in Agent outbound. `available` indicates whether that Agent can start conversations. |
| Agent's line ID | In the same Agents response, read that Agent's `lines[].providerChannelId`. | A line ID belonging to that Agent when the operation accepts `contact.providerChannelId`. Read the outbound reference for line-selection rules. |
| General provider channel | [List provider channels](https://docs.bridge.new/api-reference/provider-channels-api/get-provider-channels-by-workspace-id.md). This response publishes `provider` and `identifier`, not a channel UUID. | Use these fields only for the purposes documented by the consuming operation. Do not substitute the phone-like `identifier` for `providerChannelId`. |
| `brandId` | An Agent response can expose its `brandId`. For another flow, obtain the intended brand ID from your integration configuration or administrator; the published contract does not provide a general brand-list endpoint. | The brand ID accepted by the operation. A brand ID is not a line ID. |
| `teamId` | Obtain the intended internal team ID from your Bridge administrator or integration configuration. The published REST contract does not provide a team-list endpoint. | The documented team assignment option on conversation creation; do not also supply `participants.internals`. |
| Conversation ID | Create or retrieve a conversation and retain its returned `id`. Outbound responses contain `conversation.id`. | `{conversationId}` or `conversationId`, exactly where the operation requires it. |
| Template | [Discover a template](https://docs.bridge.new/api-reference/templates-api/discover-a-templates-agnostic-variable-inventory.md) using its ID or name. The response returns `id`, `name`, and variable keys. | Use the selector expected by the sending operation; see the next section. |
| `mediaId` | [Create presigned uploads](https://docs.bridge.new/api-reference/files-api/create-presigned-uploads-for-files.md). Each response array item has `mediaId` and `presignUrl`. Complete the required PUT upload. | The returned `mediaId` in `mediaIds`, or the media field supported by that operation. Do not send the presigned URL as a media ID. |

**Note**

  Agents lists expose line IDs in the context of each Agent. This is not a general discovery method for every workspace line. If another flow requires a `providerChannelId` you cannot obtain from the published response, ask your Bridge administrator or [support](mailto:support@sainapsis.com) for the intended line ID. Do not generate one or derive one from a telephone number.

## Similar names can require different fields

**Contact lookup** takes query parameters named `type` and `value`. An external participant in a conversation takes `identifier` and `identifierType`, plus the other fields required by that operation. Do not copy a lookup query directly into a participant body.

**Template discovery** accepts an ID or name in the path parameter `{templateId}`. **Conversation onboarding** uses `onboardingTemplates[].templateId`. **Outbound template selection** uses the `template` object's `id` or `name`; read that endpoint's schema rather than renaming every selector to `templateId`.

Use each returned variable's `key` in template `parameters`. Variable keys are not Meta slot indexes. The [template parameters guide](https://docs.bridge.new/templates-and-parameters.md) explains required values, defaults, and the difference between omitted and blank values.

## Keep result identifiers separate

| Returned value | Identifies | What it does not establish by itself |
| --- | --- | --- |
| `messageId` | A message created through the message endpoint | A provider delivery receipt |
| `trackingId` | An accepted LeadScout handoff request | Completed assignment of the requested users |
| `requestId` | An accepted Custom Connections submission | Delivery of the opening WhatsApp message |
| `eventId` | An identifier supplied with a webhook event; some event families use entity-derived values | A globally unique deduplication key or delivery-order guarantee |

Follow [Receive events](https://docs.bridge.new/webhooks/receive-events.md) for event identity and duplicate handling. See [Responses and errors](https://docs.bridge.new/guides/responses.md) for status codes, asynchronous results, and retry decisions. For a complete flow, follow [your first conversation](https://docs.bridge.new/guides/first-conversation.md) or [sending an attachment](https://docs.bridge.new/guides/send-attachments.md).

# Create a contact and send a message

Source: https://docs.bridge.new/guides/first-conversation

Follow a complete server-side flow from a Contact to a Conversation and a Message, preserving the returned identifiers.

This recipe creates a Contact, starts a Conversation with an internal Bridge User, and creates a Message. Run it on your server.

**Warning**

  Use a test Contact you are authorized to message. Creating a Conversation can run the workspace's onboarding templates before the separate Message request. Review that configuration first; setting the later Message's broadcast flag to false does not disable Conversation onboarding.

## Before you start

- Get a server-side API Key from [Authentication](https://docs.bridge.new/credentials.md).
- Obtain your workspace ID, an active WhatsApp line's `providerChannelId`, and an internal Bridge User's email. See [Identifiers and concepts](https://docs.bridge.new/guides/identifiers.md).
- Use a new test phone number in international format. If the Contact already exists, use [contact lookup](https://docs.bridge.new/api-reference/contacts-api/retrieve-a-contact-by-an-identifier.md) instead of creating it again.
- Check any required custom attributes and the workspace's onboarding sequence. This minimal example does not supply custom attributes or override templates.
- Choose `enableExternalBroadcast` explicitly: `true` requests external delivery when conversation and recipient rules permit it; `false` still creates the Message but skips external broadcast. Neither value confirms provider delivery. This flag does not override visibility or permissions.

## The sequence

| Step | Request | Value to keep |
| --- | --- | --- |
| Check access | `GET /bridge/api/health` | Successful HTTP response |
| Create Contact | `POST /bridge/api/v1/workspaces/{workspaceId}/contacts` | Contact `id` |
| Start Conversation | `POST /bridge/api/v1/workspaces/{workspaceId}/conversations` | Conversation `id` |
| Create Message | `POST /bridge/api/v1/workspaces/{workspaceId}/messages` | `messageId` |

The Contact's `id` becomes the external participant's `identifier` with `identifierType: "ID"`. The Conversation's `id` becomes the Message's `conversationId`.

## Run the example

Use Node.js with built-in `fetch`. Save this as `first-conversation.mjs`. Supply these environment variables through your server's secret and configuration settings:

| Variable | Value |
| --- | --- |
| `BRIDGE_API_KEY` | Your secret API Key |
| `BRIDGE_WORKSPACE_ID` | The intended workspace ID |
| `BRIDGE_PROVIDER_CHANNEL_ID` | The authorized WhatsApp line ID, not its phone number |
| `BRIDGE_USER_EMAIL` | An internal Bridge User in the same workspace |

}

## Understand the result

- A `201` Contact response gives you the Contact's identity and workspace. Read `type` to see its actual `NORMAL` or `PARTIAL` classification.
- A `201` Conversation response gives you the ID to use next. When no line is free, Bridge can recover a released Conversation with exactly the requested participants. That keeps its ID and history; the requested `name` and `status` are not applied in that recovery case.
- A `201` Message response supplies `messageId`. It does not by itself prove that WhatsApp delivered the message to the Contact.

This recipe explicitly assigns an internal Bridge User. For a team assignment, use the documented `teamId` option instead of `participants.internals`; they are mutually exclusive.

## If a step fails

The example stops at the failed request and never retries a write automatically. A network failure can leave the outcome uncertain. Check the relevant resource before repeating a create or send operation.

| Situation | Next action |
| --- | --- |
| Contact already exists | Use contact lookup and its returned `id`; do not keep creating the same Contact. |
| Brand or line error | Confirm the authorized line or brand with your administrator; a line's phone number is not its ID. |
| Template `0604`–`0608` | Follow [WhatsApp template parameters](https://docs.bridge.new/templates-and-parameters.md), including workspace configuration errors. |
| Message rejected because the Conversation is released | Inspect the Conversation's state and the operation's error reference before taking another action. |
| `429` | Follow [Rate limits](https://docs.bridge.new/rate-limits.md), including `Retry-After`. |

See [Responses and errors](https://docs.bridge.new/guides/responses.md) for response shapes and recovery decisions.

# Send PDFs and other attachments

Source: https://docs.bridge.new/guides/send-attachments

Send a PDF or another supported file in a conversation: calculate its checksum, upload it to the presigned URL, and attach its media ID to a Message.

To send a PDF or another supported attachment, request an upload from Bridge, upload the file bytes to the returned URL, then create a Message containing the returned `mediaId`. The complete server-side example below sends a PDF.

## Before you start

- Have an existing Conversation in the intended workspace. See [First conversation](https://docs.bridge.new/guides/first-conversation.md).
- Choose a PDF you are authorized to share and confirm it meets the [Files API](https://docs.bridge.new/api-reference/files-api/create-presigned-uploads-for-files.md) limits.
- Keep your Bridge API Key on your server. Do not add it to the presigned upload request.
- Choose the Message's `enableExternalBroadcast` flag explicitly.

## Validate the file before requesting an upload

Check the actual file on your server: its extension, MIME type and byte length must fit the published [Files API](https://docs.bridge.new/api-reference/files-api/create-presigned-uploads-for-files.md) rules. The presign request carries metadata and a checksum, not the file bytes or a size field. A `201` response prepares an upload; it is not proof that the actual bytes were inspected, that the uploaded size meets the published limits, or that a messaging provider will accept the file.

If you omit `contentType`, still copy the returned `presignUrl.headers` into the PUT request: Bridge can derive `Content-Type` from the file name. If you supply it, use the MIME type of the actual file and keep it consistent with `fileType` and the extension. Renaming a file does not convert its contents.

After PUT succeeds, upload processing may still be pending. If a Message request reports a [file upload error](https://docs.bridge.new/error-codes.md#file-upload-errors), preserve the full error and check the stage that failed before deciding whether another write is safe.

## Upload sequence

| Stage | What happens | What it does not confirm |
| --- | --- | --- |
| `POST .../files` | Bridge returns `mediaId` and `presignUrl` data. | The bytes have not been uploaded yet. |
| Presigned `PUT` | Your server sends the exact bytes using the returned upload URL and headers. | No Message has been created by this step. |
| `POST .../messages` | You attach the uploaded `mediaId` through `mediaIds`. | The API response alone does not prove provider delivery. |

The checksum is the **Base64-encoded SHA-256 digest of the complete file bytes**. It is not a hexadecimal digest and not a hash of the file name.

## Complete server-side example

Use Node.js with built-in `fetch`. Save this as `send-attachment.mjs`. Set `BRIDGE_API_KEY`, `BRIDGE_WORKSPACE_ID`, `BRIDGE_CONVERSATION_ID`, `ATTACHMENT_PATH`, and `ENABLE_EXTERNAL_BROADCAST` (`true` or `false`).

```javascript
import { readFile } from "node:fs/promises";
import { basename } from "node:path";
import { createHash } from "node:crypto";

const BASE = "https://api-connect-us.bridge.new";
function required(name) {
  const value = process.env[name];
  if (!value) throw new Error(`Set ${name} before running this example.`);
  return value;
}
const apiKey = required("BRIDGE_API_KEY");
const workspaceId = required("BRIDGE_WORKSPACE_ID");
const conversationId = required("BRIDGE_CONVERSATION_ID");
const filePath = required("ATTACHMENT_PATH");
const broadcast = required("ENABLE_EXTERNAL_BROADCAST");
if (!["true", "false"].includes(broadcast)) {
  throw new Error("ENABLE_EXTERNAL_BROADCAST must be true or false.");
}
if (!filePath.toLowerCase().endsWith(".pdf")) {
  throw new Error("This example is configured for a PDF document.");
}
const workspacePath = `/bridge/api/v1/workspaces/${encodeURIComponent(workspaceId)}`;
const bytes = await readFile(filePath);
const checksumBase64 = createHash("sha256").update(bytes).digest("base64");

async function bridgePost(path, body) {
  const response = await fetch(`${BASE}${workspacePath}${path}`, {
    method: "POST",
    headers: { "x-api-key": apiKey, "Content-Type": "application/json" },
    body: JSON.stringify(body),
  });
  const result = await response.json().catch(() => null);
  if (response.status !== 201) {
    const code = result?.code ? ` (${result.code})` : "";
    throw new Error(`Bridge ${path}: HTTP ${response.status}${code}`);
  }
  return result;
}

const uploads = await bridgePost("/files", [{
  name: basename(filePath),
  fileType: "DOCUMENT",
  contentType: "application/pdf",
  checksumBase64,
}]);
const upload = uploads?.[0];
if (!upload?.mediaId || !upload.presignUrl?.url) {
  throw new Error("The upload response is missing its mediaId or URL.");
}
const method = upload.presignUrl.method ?? "PUT";
if (method !== "PUT") throw new Error("Expected a presigned PUT upload.");
const uploadHeaders = new Headers(upload.presignUrl.headers ?? {});
const returnedChecksum = uploadHeaders.get("x-amz-checksum-sha256");
if (returnedChecksum !== null && returnedChecksum !== checksumBase64) {
  throw new Error("The returned checksum differs from the file checksum.");
}
if (returnedChecksum === null) {
  uploadHeaders.set("x-amz-checksum-sha256", checksumBase64);
}

const uploaded = await fetch(upload.presignUrl.url, {
  method,
  headers: uploadHeaders,
  body: bytes,
});
if (!uploaded.ok) {
  throw new Error(`File upload failed: HTTP ${uploaded.status}; no Message was created.`);
}

const message = await bridgePost("/messages", {
  conversationId,
  messageBody: "Here is the document you requested.",
  enableExternalBroadcast: broadcast === "true",
  mediaIds: [upload.mediaId],
});
if (!message?.messageId) throw new Error("The Message response has no messageId.");
console.log({ mediaId: upload.mediaId, messageId: message.messageId });
```

```bash
node send-attachment.mjs
```

## Keep the upload request intact

Use `presignUrl.url` without reconstructing its host, path, or query string. Use the returned method and required headers. The contract specifies `PUT` as the method's default if it is omitted, and the Files API requires `x-amz-checksum-sha256` with the same checksum sent to Bridge.

The upload sends the same `bytes` that produced the checksum. Do not convert the PDF to text, wrap it in JSON, or send a different copy of the file after hashing it.

For multiple files, preserve the association between each returned `mediaId`, its presigned data, and its corresponding file. Complete every required upload before attaching those IDs to a Message.

## Handle a failed stage

- **Bridge rejects the file request:** check the extension, `fileType`, content type, size, and checksum against the reference.
- **Upload fails:** stop before creating the Message. Check the exact URL, method, headers, checksum, and bytes. Do not assume an upload lifetime or retry policy that the response does not provide.
- **Message request fails or times out:** an uploaded file is not proof that a Message exists. Check the outcome before repeating the Message request.

`STICKER` and `WEBSITE` appear in the `FileType` enum, but the published upload table does not specify their extension, MIME, and size rules. Confirm those rules before choosing either for an integration.

See the [Files API](https://docs.bridge.new/api-reference/files-api/create-presigned-uploads-for-files.md), [Message API](https://docs.bridge.new/api-reference/messages-api/create-a-new-message.md), and [Responses and errors](https://docs.bridge.new/guides/responses.md).

# Choose and fill a WhatsApp template

Source: https://docs.bridge.new/guides/send-template

Discover a template by ID or name, supply its agnostic variable keys, and use its returned ID in a Conversation request.

Use this recipe when you want a Conversation to open with a particular WhatsApp template. The detailed [template reference](https://docs.bridge.new/templates-and-parameters.md) explains validation rules and every documented template error.

## Before you start

- Know the template's **ID or name**. Both are accepted by `GET .../templates/{templateId}`.
- Confirm the template is approved for the WhatsApp Business Account behind the intended line.
- Have an existing test Contact ID, the authorized WhatsApp `providerChannelId`, and an internal Bridge User's email. See [Identifiers and concepts](https://docs.bridge.new/guides/identifiers.md).
- Review the workspace's onboarding sequence: your override can replace the whole sequence or only its first template, depending on workspace configuration.

**Warning**

  The final request starts a Conversation and can send onboarding templates. Use an authorized test Contact and intended content.

## 1. Discover the variables

```http
GET /bridge/api/v1/workspaces/{workspaceId}/templates/{templateId}
x-api-key: YOUR_API_KEY
```

URL-encode the supplied ID or name. Read the response's `id`, `name`, `variables`, and `driftWarning`.

| Variable | Action |
| --- | --- |
| `callerMustSupply: true` | Supply a non-blank string under that variable's `key`. |
| `callerMustSupply: false`, not custom | Omit it to keep Bridge's per-Contact value. A supplied value replaces that value for every Contact. |
| `isCustom: true` | Supply your value, or omit it or send it blank to use its `default`. |

Use the agnostic `key`, never the display `label`, a Meta position, or an invented variable name. `driftWarning` is diagnostic and does not by itself block sending.

## 2. Prepare your values

Create a server-side JSON file containing only keys returned by discovery. For a template that actually declares `order_number` and `delivery_date`, it could contain:

```json
{
  "order_number": "A-10492",
  "delivery_date": "October 3"
}
```

Those two names are examples, not universal Bridge fields. Read your own template before using them. Keep values within the [WhatsApp value rules](https://docs.bridge.new/templates-and-parameters.md#whatsapp-value-rules); omit non-custom values you want Bridge to fill instead of sending blank strings.

## 3. Discover, check, and create the Conversation

Use Node.js with built-in `fetch`. Save this as `send-template.mjs` and set `BRIDGE_API_KEY`, `BRIDGE_WORKSPACE_ID`, `BRIDGE_TEMPLATE_ID_OR_NAME`, `TEMPLATE_VALUES_PATH`, `BRIDGE_CONTACT_ID`, `BRIDGE_PROVIDER_CHANNEL_ID`, and `BRIDGE_USER_EMAIL`.

```javascript
import { readFile } from "node:fs/promises";

  const value = process.env[name];
  if (!value) throw new Error(`Set ${name} before running this example.`);
  return value;
}
const apiKey = required("BRIDGE_API_KEY");
const workspaceId = required("BRIDGE_WORKSPACE_ID");
const templateRef = required("BRIDGE_TEMPLATE_ID_OR_NAME");
const contactId = required("BRIDGE_CONTACT_ID");
const providerChannelId = required("BRIDGE_PROVIDER_CHANNEL_ID");
const internalEmail = required("BRIDGE_USER_EMAIL");
const parameters = JSON.parse(await readFile(required("TEMPLATE_VALUES_PATH"), "utf8"));
if (parameters === null || Array.isArray(parameters) || typeof parameters !== "object") {
  throw new Error("The template values file must contain a JSON object.");
}
if (Object.entries(parameters).some(([key, value]) =>
  Array.from(key).length > 128 || typeof value !== "string" || Array.from(value).length > 1024
)) {
  throw new Error("Parameter keys and values must respect the published string limits.");
}
if (Object.keys(parameters).length > 50) throw new Error("At most 50 parameters are allowed.");
const workspacePath = `/bridge/api/v1/workspaces/${encodeURIComponent(workspaceId)}`;

async function request(method, path, body, expectedStatus) {
  const response = await fetch(`${BASE}${workspacePath}${path}`, {
    method,
    headers: {
      "x-api-key": apiKey,
      ...(body === undefined ? {} : { "Content-Type": "application/json" }),
    },
    ...(body === undefined ? {} : { body: JSON.stringify(body) }),
  });
  const result = await response.json().catch(() => null);
  if (response.status !== expectedStatus) {
    const code = result?.code ? ` (${result.code})` : "";
    throw new Error(`${method} ${path}: HTTP ${response.status}${code}`);
  }
  return result;
}

const template = await request(
  "GET", `/templates/${encodeURIComponent(templateRef)}`, undefined, 200,
);
if (!template?.id) throw new Error("Template discovery returned no id.");
const variables = template.variables ?? [];
const known = new Set(variables.map((variable) => variable.key));
const unknown = Object.keys(parameters).filter((key) => !known.has(key));
const missing = variables.filter((variable) =>
  variable.callerMustSupply &&
  (typeof parameters[variable.key] !== "string" || !parameters[variable.key].trim())
);
if (unknown.length || missing.length) {
  throw new Error(`Check template keys: ${unknown.length} unknown, ${missing.length} missing.`);
}

const conversation = await request("POST", "/conversations", {
  participants: {
    externals: [{
      identifier: contactId,
      identifierType: "ID",
      messageProviderType: "WHATSAPP",
      providerChannelId,
    }],
    internals: [{ identifier: internalEmail, identifierType: "EMAIL" }],
  },
  onboardingTemplates: [{ templateId: template.id, parameters }],
}, 201);
if (!conversation?.id || conversation.workspaceId !== workspaceId) {
  throw new Error("The Conversation response does not identify the intended workspace.");
}
console.log({ templateId: template.id, conversationId: conversation.id });
```

| Error | What to do |
| --- | --- |
| Discovery `BRIDGE_TEMPLATE_0001` | Check the ID/name and workspace. This response does not reveal whether another workspace owns that identifier. |

# Start an Agent outbound conversation

Source: https://docs.bridge.new/guides/agent-outbound

Choose an Agent, send an opening template, understand forceSend and recovery, and request a LeadScout handoff.

Use outbound when an existing Contact should receive an approved WhatsApp template and continue with an AI Agent. Use [create a conversation](https://docs.bridge.new/guides/first-conversation.md) for the general conversation workflow.

## Choose the operation

| Your goal | Operation | How the Agent is selected |
| --- | --- | --- |
| Start with a specific LeadScout or Service Agent | `POST /bridge/api/v1/workspaces/{workspaceId}/agents/{agentId}/outbound` | You supply the Agent ID from `GET /agents`. |
| Start with a LeadScout selected through the workspace's eligible lines | `POST /bridge/api/v1/workspaces/{workspaceId}/leadscout/outbound` | Bridge resolves the prospecting Agent for the line. |

Both use the REST API host `https://api-connect-us.bridge.new` and a server-side `x-api-key`. They have separate request schemas. Read the [Agents outbound reference](https://docs.bridge.new/api-reference/agents-api/start-an-outbound-conversation-with-a-contact-as-a-given-agent.md) or [LeadScout outbound reference](https://docs.bridge.new/api-reference/leadscout-api/initiate-a-leadscout-outbound-conversation-with-a-known-lead.md) for the operation you use.

## Before you send

1. [Look up the Contact](https://docs.bridge.new/api-reference/contacts-api/retrieve-a-contact-by-an-identifier.md), or [create it](https://docs.bridge.new/api-reference/contacts-api/create-a-new-contact.md) if missing. Outbound requires a Contact that already exists in the workspace; you do not need to create a separate Conversation or Message first.
2. [List Agents](https://docs.bridge.new/api-reference/agents-api/list-the-agents-of-a-workspace.md). Choose an available Agent and read its `lines[].providerChannelId`. An AI Agent ID differs from a human Bridge User ID.
3. Choose an approved template. [Discover its variables](https://docs.bridge.new/guides/send-template.md#1-discover-the-variables), supply caller-required values, and check that it is approved for the destination line. Use only the discovery step as this prerequisite; the separate Conversation-creation step in that recipe is not needed for outbound.
4. Confirm that your business has the required opt-in. If you send `consent.status: "GRANTED"`, include `capturedAt`; this records your assertion of consent.

For Agents outbound, `contact.providerChannelId` must belong to the chosen Agent when supplied. It is a preference: another eligible Agent line can be selected. For LeadScout outbound, an explicit line is respected. [Identifiers and their sources](https://docs.bridge.new/guides/identifiers.md) explains which values to use.

## Send a minimal Agent request

Replace every placeholder. This example assumes the chosen template has no unresolved caller-required variables. Set `forceSend` deliberately; the example keeps the default behavior explicit.

```bash
curl --fail-with-body --request POST \
  "https://api-connect-us.bridge.new/bridge/api/v1/workspaces/$WORKSPACE_ID/agents/$AGENT_ID/outbound" \
  --header "x-api-key: $BRIDGE_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "contact": {
      "identifier": "f0000001-0000-4000-8000-000000000001",
      "identifierType": "ID",
      "messageProviderType": "WHATSAPP"
    },
    "template": {
      "id": "f0000040-0000-4000-8000-000000000040"
    },
    "forceSend": false
  }'
```

A successful request returns `201`. Store `conversation.id` and interpret these response fields:

| Field | Meaning |
| --- | --- |
| `alreadyInitiated: true` | An existing active conversation was reused. The successful request still adds its new template and follow-ups. |
| `recovered: true` | A released, recoverable conversation was recovered, retaining its ID. Its previous outbound context and `agentContext` are replaced. |
| `additionalMessagesPersisted` | The number of follow-up messages stored. This is not a delivery receipt. |
| `templateSent` | A summary of the opening template stored for sending. Do not interpret the field name as proof of recipient delivery. |

New creation has neither reuse nor recovery set to true. Recovery can happen with `forceSend: false`. Additional messages are persisted in request order; do not rely on a promise that they wait for the Contact to reply. The shared outbound flow persists text follow-ups and does not attach their `mediaIds`. Use the documented `template.media` option for media on the opening template, or the [Message attachment workflow](https://docs.bridge.new/guides/send-attachments.md) for a separate message.

## What forceSend does

Availability is evaluated for **this Contact's conversation on each line**. An occupied line here does not mean the corporate WhatsApp line is globally reserved for one Contact.

The following rules remain subject to Agent availability, template validation, consent validation and session checks.

On a narrow screen, scroll horizontally to compare all four choices. Keyboard users can focus this comparison and use the arrow keys.

| Situation | LeadScout: false | LeadScout: true | Agents: false | Agents: true |
| --- | --- | --- | --- | --- |
| Selected line is free | Create | Create | Create | Create |
| Selected line holds a released conversation marked recoverable | Recover the same ID | Recover the same ID | Recover the same ID | Recover the same ID |
| Automatic selection finds only occupied, active conversations | `409 …0008` | Reuse the first eligible occupied conversation | `409 …0008` | Prefer one controlled by the requested Agent, then apply the controller check below |
| Explicit line is occupied | `409 …0007` | Reuse that conversation | Try other free or recoverable Agent lines; otherwise `409 …0008` | Try other free or recoverable Agent lines; otherwise prefer an occupied line the Agent controls |
| Selected occupied conversation is controlled by a human or another Agent | No active reuse | Legacy route permits reuse, subject to other checks; this does not itself promise a controller transfer | No active reuse | `409 BRIDGE_AI_AGENT_OUTBOUND_0006`; this rejection writes nothing |
| Only blocked or released, nonrecoverable conversations are available | `409 …0008` | `409 …0008` | `409 …0008` | `409 …0008` |

In this table, `…0007` is `BRIDGE_AI_LEADSCOUT_0007` and `…0008` is `BRIDGE_AI_LEADSCOUT_0008`. A released conversation is recoverable only when its stored recovery flag permits it; `forceSend` does not make it recoverable.

For both routes, a LeadScout session that is still open and unexpired blocks a new outbound request with `409 BRIDGE_AI_LEADSCOUT_0017`. Failure to finalize an expired session returns `409 BRIDGE_AI_LEADSCOUT_0018`. A Service Agent can continue its open, unexpired service session; an expired session is closed before a new one opens.

**Warning**

  `forceSend` is not an idempotency key. Repeating a successful request can add another template and more messages. It does not bypass blocked conversations, session checks, approval rules or validation. A timeout leaves the outcome uncertain: inspect the conversation before deciding whether to submit again.

## Handle conflicts and partial work

| Result | Next step |
| --- | --- |
| `BRIDGE_AI_LEADSCOUT_0007` / `0008` | Check the Contact's existing conversation and eligible lines. Decide whether reuse is appropriate before enabling `forceSend`. |
| `BRIDGE_AI_AGENT_OUTBOUND_0006` | Inspect `extra.conversationId` and its controller. Coordinate ownership before deliberately releasing it. Do not automatically interrupt a human conversation. |
| `BRIDGE_AI_LEADSCOUT_0017` / `0018` | Resolve the existing session or contact support. Switching `forceSend` to true does not fix the session. |
| `BRIDGE_AI_LEADSCOUT_0019` / `0020` / `0021` | Correct missing, conflicting or unknown template variables using discovery. |
| `400 BRIDGE_AI_LEADSCOUT_0016` for an unknown template `mediaId` on Agents outbound | The conversation may already have been created or recovered before this error. Inspect it before retrying. |

[Release conversation](https://docs.bridge.new/api-reference/conversations-api/release-conversation.md) is a separate operation with business effects. A `204` has no response body. Release only when ending that conversation is your intended action.

## Request a LeadScout handoff to a human

For a LeadScout conversation, resolve the human's [Bridge User ID or email](https://docs.bridge.new/guides/identifiers.md), then call the [manual handoff endpoint](https://docs.bridge.new/api-reference/leadscout-api/request-a-manual-handoff-of-a-leadscout-conversation-to-internal-users.md). This operation is specific to LeadScout; do not assume it applies to a Service Agent.

```bash
curl --fail-with-body --request POST \
  "https://api-connect-us.bridge.new/bridge/api/v1/workspaces/$WORKSPACE_ID/leadscout/conversations/$CONVERSATION_ID/handoff" \
  --header "x-api-key: $BRIDGE_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "assignees": [
      {"identifier": "f0000002-0000-4000-8000-000000000002", "identifierType": "ID"}
    ]
  }'
```

A `202` acknowledges the request. Save its `trackingId` and `conversationId`; acceptance does not prove that assignment has completed or that a human has read or answered the conversation. The reference does not publish a handoff tracking endpoint, so do not construct one from `trackingId`.

Continue with [error handling](https://docs.bridge.new/error-codes.md) and [webhook receiving](https://docs.bridge.new/webhooks/receive-events.md) to connect this workflow to your system.

# Read every page of results

Source: https://docs.bridge.new/guides/pagination

Follow opaque cursors across Contacts, Conversations, Bridge Users, and Agents without stopping on a short page.

List endpoints return a collection and an optional `cursor`. Send that cursor unchanged to read the next page. Keep following cursors until it is null or absent.

## Choose the collection

All four endpoints below accept `limit` from **1 to 100**, with a default of **20**.

| Resource | Path after the workspace | Collection field |
| --- | --- | --- |
| Contacts | `/contacts` | `contacts` |
| Conversations | `/conversations` | `conversations` |
| Bridge Users | `/users` | `users` |
| Agents | `/agents` | `agents` |

Use [contact lookup](https://docs.bridge.new/api-reference/contacts-api/retrieve-a-contact-by-an-identifier.md) or [Bridge User lookup](https://docs.bridge.new/api-reference/internal-users-api/retrieve-an-internal-user-by-an-identifier.md) when you need one known person. A full list sweep is a different task.

## Server-side example

This example reads Contacts. Save it as `list-contacts.mjs` and set `BRIDGE_API_KEY` and `BRIDGE_WORKSPACE_ID` on your server.

The local `maxPages` guard prevents an accidentally unbounded run; it is not a Bridge API limit. The repeated-cursor guard stops and reports a problem rather than silently returning an incomplete list.

```javascript
const BASE = "https://api-connect-us.bridge.new";
const apiKey = process.env.BRIDGE_API_KEY;
const workspaceId = process.env.BRIDGE_WORKSPACE_ID;
if (!apiKey || !workspaceId) {
  throw new Error("Set BRIDGE_API_KEY and BRIDGE_WORKSPACE_ID.");
}

async function* pages(resource, collection, filters = {}) {
  let cursor;
  const seen = new Set();
  const maxPages = 10000;

  for (let pageNumber = 0; pageNumber < maxPages; pageNumber += 1) {
    const url = new URL(
      `/bridge/api/v1/workspaces/${encodeURIComponent(workspaceId)}/${resource}`,
      BASE,
    );
    for (const [key, value] of Object.entries(filters)) {
      url.searchParams.set(key, String(value));
    }
    url.searchParams.set("limit", "100");
    if (cursor !== undefined) url.searchParams.set("cursor", cursor);

    const response = await fetch(url, { headers: { "x-api-key": apiKey } });
    const body = await response.json().catch(() => null);
    if (response.status !== 200) {
      const code = body?.code ? ` (${body.code})` : "";
      throw new Error(`List ${resource}: HTTP ${response.status}${code}`);
    }
    if (!Array.isArray(body?.[collection])) {
      throw new Error(`Expected the ${collection} collection.`);
    }

    yield body[collection];
    if (body.cursor === null || body.cursor === undefined) return;
    if (typeof body.cursor !== "string" || seen.has(body.cursor)) {
      throw new Error("Invalid or repeated cursor; stopped without claiming completion.");
    }
    seen.add(body.cursor);
    cursor = body.cursor;
  }
  throw new Error("Local page guard reached; the sweep is incomplete.");
}

let count = 0;
for await (const contacts of pages("contacts", "contacts")) {
  // Process or store this page before continuing. Avoid logging personal data.
  count += contacts.length;
}
console.log({ contactsRead: count });
```

```bash
node list-contacts.mjs
```

Use `pages("conversations", "conversations", { status: "ACTIVE" })`, `pages("users", "users")`, or `pages("agents", "agents")` with the corresponding contract. Keep the same filters throughout one traversal.

## Do not stop on a short page

A page containing fewer records than `limit` can still have another page. The Agents endpoint explicitly documents this behavior. The returned cursor is the continuation signal; collection length is not.

Treat the cursor as opaque. Do not decode it, increment it, or build one yourself. `URL.searchParams` in the example preserves its value through URL encoding.

## Filters and rate limits

- The Contact list's `ownerEmail` and `search` filters are deprecated. For a known email or phone, use contact lookup. To filter an inventory by `ownerId`, read that field from the returned rows in your own code.
- The Bridge User list's `email` and `status` filters are deprecated. Use lookup for a known email, or inspect each returned User's `status`.
- Each page request consumes the workspace's shared request budget. Follow [Rate limits](https://docs.bridge.new/rate-limits.md), including `Retry-After` on `429`. This minimal example stops on non-200 responses instead of retrying automatically.

The published contracts do not promise a transactional snapshot of a list while records are changing. Do not describe this traversal as a guaranteed consistent export or infer an undocumented cursor lifetime.

# Responses, errors, and retries

Source: https://docs.bridge.new/guides/responses

Interpret creation, acceptance, empty responses, validation errors, and retry signals without confusing the REST and Custom Connections contracts.

## Read the result for this operation

The HTTP status and response body describe the operation you called. They do not all mean that a person received a message.

| Operation | Published success | What to do with it |
| --- | --- | --- |
| Create a message | `201`, with `messageId` | Retain the message ID. The published response does not include a provider delivery receipt; do not label it delivered from this response alone. |
| Release a conversation | `204`, with no response body | Treat it as success and do not call a JSON parser on the empty body. |
| Request LeadScout handoff | `202`, with `trackingId`, `conversationId`, `status`, and `assignees` | Retain the correlation ID. Assignment is asynchronous; assignees echo the request and do not prove that downstream resolution or assignment completed. |
| Submit a Custom Connections lead | `202`, with `requestId` | Retain the request ID. Show that the lead was accepted; the opening WhatsApp message is sent later by a separate service. |

The reference for each operation remains authoritative: [messages](https://docs.bridge.new/api-reference/messages-api/create-a-new-message.md), [release](https://docs.bridge.new/api-reference/conversations-api/release-conversation.md), [handoff](https://docs.bridge.new/api-reference/leadscout-api/request-a-manual-handoff-of-a-leadscout-conversation-to-internal-users.md), and [Custom Connections](https://docs.bridge.new/api-reference/campaign-leads/register-a-campaign-lead.md).

**Note**

  A correlation ID is not a status URL. The published contract does not define a polling endpoint for `trackingId` or `requestId`. Keep it for correlation and support; do not construct a new endpoint from it.

## Parse the error shape the endpoint publishes

REST Integrations and Custom Connections have separate error contracts.

### REST Integrations

Many responses use `Problem`: `title` and `status` are required; `code`, `detail`, `errors`, `traceId`, `instance`, and `extra` are optional. When a `code` is present, use it to select a documented error handler rather than matching the human-readable `title`. Keep `traceId` when provided for a support request.

Some published validation responses declare `HTTPValidationError`, whose `detail` is an array of entries with `loc`, `msg`, and `type`. The shared API error handler reviewed for this documentation returns request validation details as `Problem.errors[]` instead. The published response definitions are preserved; confirmation against the deployed API is still pending. See the [validation compatibility note](https://docs.bridge.new/error-codes.md#parse-validation-errors-defensively).

Accept JSON errors with either `application/json` or `application/problem+json`. Inspect a `code` when present, then an `errors` array or a `detail` array for field errors. A string `detail` is an explanation, not an array. A `422` status alone does not identify one universal body shape. Keep a fallback for an error without `code`, and use the endpoint reference together with [Error codes](https://docs.bridge.new/error-codes.md) to choose the action.

### Custom Connections

Its error body has required `type`, `title`, and `status`, and may include `detail`. Here **`type` is the machine-readable error identifier**. It is not the REST `code` field. The [Custom Connections error reference](https://docs.bridge.new/lead-capture/errors.md) lists these responses.

Error responses do not carry the submission `requestId`; only a successful `202` does. For an error support request, retain the page URL and approximate time as described in that reference.

## Make retry decisions by operation and cause

| Result | Next action |
| --- | --- |
| REST `429` | Follow `Retry-After` in seconds. The rate-limit guide states that the rejected request was not processed. The workspace budget is shared across API Keys. |
| REST `401` or `403` | Correct the API Key, permissions, or workspace mismatch. A timed retry does not fix those causes. |
| Validation or configuration error | Correct the documented cause first. Do not repeatedly send the same invalid request. |
| Custom Connections `422` | The documented cause is CAPTCHA provider unavailability. Its error guide says retrying is safe; mint a fresh CAPTCHA token for the new attempt. |
| Custom Connections CAPTCHA rejection | Check that the token is present, fresh, and minted for this attempt. The same error also covers a low score, so a new attempt alone does not prove the original cause. |
| Timeout, connection loss, or an unclassified `5xx` during a mutation | Do not assume nothing happened. Inspect the operation's documented effects and any identifiers already obtained before deciding whether to repeat it. Do not assume a general idempotency guarantee. |

See [Rate limits](https://docs.bridge.new/rate-limits.md) for pacing and [Custom Connections errors](https://docs.bridge.new/lead-capture/errors.md) for its distinct retry rules.

## Some failures can follow a write

The [Agent outbound reference](https://docs.bridge.new/api-reference/agents-api/start-an-outbound-conversation-with-a-contact-as-a-given-agent.md) documents that an unknown `template.media.mediaId` can produce `BRIDGE_AI_LEADSCOUT_0016` after the conversation was created or recovered. A retry may therefore produce a different result.

This is why a failure status alone is not a universal rollback guarantee. Follow the effects and recovery instructions for the specific operation. If those instructions are unclear or conflict, identify the uncertainty and contact [Bridge support](mailto:support@sainapsis.com) before retrying an action with external effects.

# WhatsApp template parameters

Source: https://docs.bridge.new/templates-and-parameters

Open a conversation with your own WhatsApp templates, fill their variables, and handle every error the request can return.

## Overview

When you create a conversation, `onboardingTemplates` lets you choose the WhatsApp templates it opens with, in order. A template can contain variables — an order number, a delivery date, the Contact's first name. Some of them Bridge fills on its own for each Contact; others only you can provide, and you send them in the entry's `parameters`.

The flow has three steps:

1. Look up the template's variables.
2. Decide which values to send.
3. Send them with `POST .../conversations`.

**Note**

  Every check described on this page runs before anything is created. If the request is rejected, **no conversation is created and no message is sent**, so you can correct it and send it again.

---

## 1. Find the template's variables

```http
GET /bridge/api/v1/workspaces/{workspaceId}/templates/{templateId}
x-api-key: YOUR_API_KEY
```

`templateId` accepts either the template's `id` or its `name`. The response lists its variables:

```json
{
  "id": "f0000040-0000-4000-8000-000000000040",
  "name": "order_shipped_promo",
  "language": "es",
  "driftWarning": { "hasDrift": false, "stale": [], "missingLabels": [] },
  "variables": [
    { "key": "first_name", "label": "Contact first name", "callerMustSupply": false, "isCustom": false, "default": null },
    { "key": "order_number", "label": "Order number", "callerMustSupply": true, "isCustom": false, "default": null },
    { "key": "delivery_date", "label": "Delivery date", "callerMustSupply": true, "isCustom": false, "default": null },
    { "key": "tracking_code", "label": "Tracking code", "callerMustSupply": false, "isCustom": true, "default": "pending" }
  ]
}
```

`driftWarning` is diagnostic only: it reports differences between the declared variables and Meta's template snapshot and never blocks a send. The table below describes each item in `variables`.

| Field | Meaning |
| ----- | ------- |
| `key` | The name to use in `parameters` |
| `label` | A human-readable description of the variable |
| `callerMustSupply` | `true` when you must supply a non-blank value because Bridge has no source for it; `false` otherwise |
| `isCustom` | Whether this is a custom variable: a value only you know, with a default text |
| `default` | For a custom variable, the text sent when you send no value for it; `null` otherwise |

A template that is not in your workspace returns `404` with `BRIDGE_TEMPLATE_0001`.

---

## 2. Decide which values to send

| Variable | What it means | What to do |
| -------- | ------------- | ---------- |
| `callerMustSupply: true` | Bridge has no source for this value | **Required.** Send a non-blank value for its `key` |
| `callerMustSupply: false`, `isCustom: false` | Bridge fills it for each Contact, such as the Contact's first name | **Optional.** Omit it to keep Bridge's value |
| `isCustom: true` | A value only you know, with a `default` | **Optional.** Send your value, or omit it (or send it blank) and its `default` is sent |

A value you send for a `callerMustSupply: false` variable replaces Bridge's value and is used **for every Contact** in the conversation.

**Warning**

  For a variable that is not custom, keep Bridge's value by **omitting the key**. A blank value is not treated as "use the default": it is sent as you wrote it. A required variable with a blank or whitespace-only value is rejected as missing. Only custom variables (`isCustom: true`) treat a blank value as not sent and fall back to their `default`.

---

## 3. Send the parameters

Each entry in `onboardingTemplates` takes the template's `id` (as returned in step 1) and its `parameters`, keyed by variable `key`. Position in the list sets the sending order.

```http
POST /bridge/api/v1/workspaces/{workspaceId}/conversations
x-api-key: YOUR_API_KEY
Content-Type: application/json
```

```json
{
  "participants": {
    "externals": [
      {
        "identifier": "+13802098869",
        "identifierType": "PHONE",
        "messageProviderType": "WHATSAPP",
        "brandId": "YOUR_BRAND_ID"
      }
    ]
  },
  "onboardingTemplates": [
    {
      "templateId": "f0000040-0000-4000-8000-000000000040",
      "parameters": {
        "order_number": "A-10492",
        "delivery_date": "3 de octubre"
      }
    }
  ]
}
```

In this example `first_name` and `tracking_code` are omitted, so each Contact receives their own first name and `tracking_code` is sent as its default, `pending`.

Limits per template: at most **50** parameters, keys up to **128** characters, values up to **1,024** characters. Requests beyond these limits are rejected as malformed (see [Errors](https://docs.bridge.new/templates-and-parameters.md#errors)).

Depending on how the workspace is set up, your templates replace its whole onboarding sequence or only its first template. In the second case, the rest of the configured sequence is still sent after yours.

---

## WhatsApp value rules

WhatsApp rejects some values when the message is sent. Bridge checks them up front so the request fails while you can still fix it:

| Rule | Limit |
| ---- | ----- |
| Line breaks and tabs | Not allowed — no `\n`, `\r` or `\t` |
| Consecutive spaces | At most 4 in a row |
| Header | The header text with your value in place fits in **60** characters |
| URL button | The button's link with your value in place fits in **2,000** characters |
| Body | The body text plus all its values fits in **1,024** characters |

**Warning**

  The body limit includes the values Bridge fills in for each Contact, such as their first name. Bridge can only check the values it can see when you make the request, so leave room for them.

Bridge never trims or rewrites your values: what you send is what the Contact receives.

---

## Errors

All errors use the `application/problem+json` format described in [Error codes](https://docs.bridge.new/error-codes.md). Branch on `code`, never on `title`.

| Code | Status | When | `extra` |
| ---- | ------ | ---- | ------- |
| `BRIDGE_CONVERSATION_0601` | 404 | The template does not exist | `templateId`, `workspaceId` |
| `BRIDGE_CONVERSATION_0602` | 400 | The template belongs to another workspace | `templateId`, `workspaceId` |
| `BRIDGE_CONVERSATION_0603` | 400 | The template is not approved for the line a participant will be reached on | `templateId`, `workspaceId`, `userIds` (the Contacts whose line it is not approved for, when known) |
| `BRIDGE_CONVERSATION_0604` | 422 | A required variable is missing or blank | `templateId`, `missingVariables: [{key, label}]` |
| `BRIDGE_CONVERSATION_0605` | 422 | A key in `parameters` is not one of the template's variables | `templateId`, `unknownKeys: [key]` |
| `BRIDGE_CONVERSATION_0606` | 422 | `parameters` was sent for a template that is not a WhatsApp template | `templateId` |
| `BRIDGE_CONVERSATION_0607` | 422 | A value breaks a [WhatsApp rule](https://docs.bridge.new/templates-and-parameters.md#whatsapp-value-rules) | `templateId`, `invalidVariables: [{key, label, reason}]` |
| `BRIDGE_CONVERSATION_0608` | 422 | A template the workspace sends after yours needs values only the caller can provide | `templateId`, `origin: "WORKSPACE_CONFIGURATION"` |

### Missing values — `0604`

```json
{
  "title": "A template named in the onboarding override is missing values only the caller can provide",
  "status": 422,
  "detail": "A template named in the onboarding override is missing values only the caller can provide",
  "code": "BRIDGE_CONVERSATION_0604",
  "extra": {
    "templateId": "f0000040-0000-4000-8000-000000000040",
    "missingVariables": [
      { "key": "delivery_date", "label": "Delivery date" }
    ]
  }
}
```

### Invalid values — `0607`

```json
{
  "title": "Parameter values for an onboarding template break a WhatsApp rule and would be rejected when sent",
  "status": 422,
  "detail": "Parameter values for an onboarding template break a WhatsApp rule and would be rejected when sent",
  "code": "BRIDGE_CONVERSATION_0607",
  "extra": {
    "templateId": "f0000040-0000-4000-8000-000000000040",
    "invalidVariables": [
      { "key": "order_number", "label": "Order number", "reason": "NEWLINE" }
    ]
  }
}
```

`reason` is the first rule the value breaks:

| `reason` | Meaning |
| -------- | ------- |
| `NEWLINE` | The value contains `\n` or `\r` |
| `TAB` | The value contains `\t` |
| `CONSECUTIVE_SPACES` | The value has more than 4 spaces in a row |
| `TOO_LONG` | The header or URL button exceeds its limit with the value in place |
| `BODY_TOO_LONG` | The body exceeds 1,024 characters; every body value you sent is listed |

### `0608` is not fixed by changing the request

`BRIDGE_CONVERSATION_0608` only occurs in workspaces where your templates replace just the first template of the onboarding sequence. It means a template the workspace sends after yours needs values that only the caller can provide, and the API cannot supply them. Ask a workspace admin to change the onboarding sequence.

### Malformed requests

A request that does not match the schema — more than 50 parameters, a key over 128 characters, a value over 1,024, or an unknown field — is rejected with `422` **without a `code`**. It carries an `errors` list pointing at each problem instead:

```json
{
  "title": "Unprocessable content",
  "status": 422,
  "errors": [
    {
      "loc": ["body", "onboardingTemplates", 0, "parameters", "order_number"],
      "msg": "String should have at most 1024 characters",
      "type": "string_too_long"
    }
  ]
}
```

### Evaluation order

Checks run in this order, and **the first error wins**:

1. Rate limit — `429`
2. Request shape — `422` without `code`
3. Participants, brand and line — `400` / `409`, for example `BRIDGE_BRAND_0101` or `BRIDGE_PROVIDER_CHANNEL_0001`
4. Each template, in list order: `0601` / `0602` → `0603` → `0606` → `0605` → `0604` → `0607`
5. `0608`, only in workspaces where your templates replace just the first template

So fixing one error can reveal the next. Values for a later template are not checked until every earlier template passes.

# Rate limits

Source: https://docs.bridge.new/rate-limits

How many requests the Bridge API accepts, the headers that tell you where you stand, and how to handle a 429 correctly.

## Overview

The Bridge API accepts **50 requests every 5 seconds**. The limit applies to every endpoint, is enabled by default, and needs no configuration.

**Note**

  The budget belongs to the **workspace**, not to the API Key. If you issue several keys for the same workspace — one per application, as recommended — they all draw from the same 50 requests.

---

## Knowing where you stand

Every response to an authenticated request carries two headers, so you never have to guess how much budget is left:

```http
RateLimit-Policy: "default";q=50;w=5
RateLimit: "default";r=43;t=3
```

| Field | Meaning |
| ----- | ------- |
| `q` | Requests allowed per window |
| `w` | Window length, in seconds |
| `r` | Requests **remaining** in the current window |
| `t` | Seconds until the window resets and `r` returns to `q` |

A client that watches `r` and pauses as it approaches zero is never rejected at all.

**Note**

  A request rejected **before** authentication — a missing or invalid API Key — carries neither header. See [Authentication](https://docs.bridge.new/credentials.md) for those responses.

---

## When you go over

Requests beyond the budget are answered with `429 Too Many Requests`. Nothing is processed, so the request is safe to repeat.

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 3
RateLimit-Policy: "default";q=50;w=5
RateLimit: "default";r=0;t=3
```

```json
{
  "title": "Too Many Requests",
  "status": 429,
  "detail": "The workspace has exhausted its request budget for the current window",
  "code": "BRIDGE_RATE_LIMIT_0001"
}
```

`Retry-After` is expressed in **seconds from now**, not as a date. Wait that long and the next request is served.

**Warning**

  **A `429` is not an authentication problem.** `401` and `403` mean the API Key is missing, invalid, expired or not authorized, and **retrying them on a schedule will never succeed** — it only burns your budget. Only `429` should be retried automatically, and only after the delay it gives you.

---

## What consumes budget

Every HTTP request counts as one, including requests that end in a validation error or a `404`. What matters is how many calls your client makes, not how much data comes back.

That distinction shows up when you read:

- **A single resource by id** — `GET .../contacts/{contactId}` — costs **one request**, whatever the size of the response.
- **A list** — `GET .../contacts` — costs **one request per page**. Reading a list in full costs as many requests as it has pages.

So page size decides the cost of a full sweep. Walking 500 contacts costs 5 requests at 100 per page, and 25 requests at 20 per page — same data, five times the budget.

**Note**

  Prefer the largest page size an endpoint accepts when you are reading a list in full, and read a single resource by its id when you already know which one you need.

---

## Backing off in practice

A client that paces itself from `RateLimit` and honours `Retry-After` on the rare miss needs no other logic:

```python
import time

import requests

BASE = "https://api-connect-us.bridge.new"
HEADERS = {"x-api-key": "YOUR_API_KEY"}


def rate_limit_state(response):
    header = response.headers.get("RateLimit", "")
    fields = dict(part.split("=", 1) for part in header.split(";") if "=" in part)
    return int(fields.get("r", 1)), int(fields.get("t", 1))


def get(path):
    while True:
        response = requests.get(f"{BASE}{path}", headers=HEADERS)

        if response.status_code == 429:
            time.sleep(int(response.headers["Retry-After"]))
            continue

        remaining, reset_in = rate_limit_state(response)
        if remaining == 0:
            time.sleep(reset_in)

        return response
```

```javascript
const BASE = "https://api-connect-us.bridge.new";
const HEADERS = { "x-api-key": "YOUR_API_KEY" };

const sleep = (seconds) => new Promise((done) => setTimeout(done, seconds * 1000));

function rateLimitState(response) {
  const fields = Object.fromEntries(
    (response.headers.get("RateLimit") ?? "")
      .split(";")
      .filter((part) => part.includes("="))
      .map((part) => part.split("="))
  );
  return { remaining: Number(fields.r ?? 1), resetIn: Number(fields.t ?? 1) };
}

async function get(path) {
  while (true) {
    const response = await fetch(`${BASE}${path}`, { headers: HEADERS });

    if (response.status === 429) {
      await sleep(Number(response.headers.get("Retry-After")));
      continue;
    }

    const { remaining, resetIn } = rateLimitState(response);
    if (remaining === 0) await sleep(resetIn);

    return response;
  }
}
```


**Warning**

  Do not retry a `429` immediately or on a fixed timer of your own. Retrying before `Retry-After` elapses is rejected again, and a tight retry loop keeps the workspace at zero budget for every other application sharing it.

---

## Standards

These fields are not Bridge-specific: `RateLimit-Policy` and `RateLimit` follow the IETF [RateLimit header fields](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/) specification, `Retry-After` is [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#field.retry-after), and the `429` body is [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html). If you already handle `X-RateLimit-*` headers from another API, these are the standardised equivalents.

When the two disagree, **`Retry-After` wins** — it is the authoritative retry signal, and `RateLimit` is pacing information.

# Error codes

Source: https://docs.bridge.new/error-codes

Interpret REST API error codes, validation responses and uncertain write outcomes, and choose the next action.

## Response format

Example of a `Problem` response. Consult the endpoint reference for its HTTP status, media type and response schema:

```json
{
  "title": "A template named in the onboarding override is missing values only the caller can provide",
  "status": 422,
  "detail": "A template named in the onboarding override is missing values only the caller can provide",
  "code": "BRIDGE_CONVERSATION_0604",
  "extra": {
    "templateId": "f0000040-0000-4000-8000-000000000040",
    "missingVariables": [{ "key": "delivery_date", "label": "Delivery date" }]
  },
  "instance": "https://api-connect-us.bridge.new/bridge/api/v1/workspaces/{workspaceId}/conversations",
  "traceId": "Root=1-6702b8c4-3f1a2b4c5d6e7f8091a2b3c4"
}
```

| Field | Meaning |
| ----- | ------- |
| `code` | When present, the stable error code listed on this page. **Branch on this field rather than the title.** Validation and server errors may omit it. |
| `title` | A human-readable message. It may be longer than the title shown in the tables below, so never match on it |
| `status` | The HTTP status code |
| `detail` | More detail about this occurrence, when available |
| `extra` | Machine-readable context for the error, such as the ids or keys involved, when available |
| `instance` | The request URL |
| `traceId` | Include it when you contact support |

**Note**

  Read the response schema for the operation you call. Where it is `HTTPValidationError`, validation details are in a `detail` array; each entry contains `loc` (where), `msg` (what) and `type`. Other documented `422` responses use `Problem` and may include a `code` and `extra`. Do not assume all `422` responses have the same shape.

### Parse validation errors defensively

Accept JSON error bodies with either `application/json` or `application/problem+json`. Check the HTTP status first, then inspect the body:

1. If `code` is present, use the matching entry on this page to choose the action.
2. If `errors` is an array, read its `loc`, `msg` and `type` entries as validation details.
3. If `detail` is an array, read it as the `HTTPValidationError` form. A string `detail` is an explanation, not a list of field errors.
4. Preserve `traceId`, status and the request URL for support. Do not require `code` or `extra` to exist, and do not match human-readable messages as identifiers.

### Legacy code strings

Some legacy error handlers append a symbolic name to `code`, for example `BRIDGE_PRELOAD_FILE_0002 | PRELOAD_FILE_IS_PENDING`. Preserve the complete received value for logs and support. For catalog lookup, accept a known bare code or its explicitly recognized legacy form; do not compare human-readable `title` or `detail`, invent an unknown code, or rewrite the response body. The current deployed handler version has not been independently confirmed by this source review.

**Warning**

  **Validation compatibility:** some published OpenAPI responses declare `HTTPValidationError.detail[]` and `application/json`, while the shared API error handler reviewed for this documentation returns validation details as `Problem.errors[]` with `application/problem+json`. This editorial update preserves those published response definitions. Handle both forms; confirmation against the deployed API remains pending before choosing one as the only accepted form in a strict generated client.

### Decide whether to retry

| Result | Action |
| --- | --- |
| `400` or `422` | Correct the request using the code and field errors. Repeating unchanged input does not fix validation. |
| `401` or `403` | Check the credential, workspace and permissions for the correct integration surface. Keep REST API keys on your server. |
| `404` | Confirm the identifier and workspace. A lookup that finds no Contact is different from malformed input. |
| `409` | Read the operation's code: an existing conversation, unavailable Agent or unfinished session needs a different resolution. Do not enable `forceSend` automatically. |
| `429` | Follow the [rate-limit headers and backoff guidance](https://docs.bridge.new/rate-limits.md). |
| Timeout, disconnected response or `5xx` after a write | Treat the outcome as uncertain. Inspect the affected resource before resubmitting; an error does not prove that no work was persisted. |

The general retry guidance does not add idempotency to an endpoint. For outbound reuse, recovery and partial writes, see [Agent outbound and handoff](https://docs.bridge.new/guides/agent-outbound.md). Custom Connections has its own [error reference](https://docs.bridge.new/lead-capture/errors.md) and no REST API key.

## Finding a contact or a user by an identifier

**Warning**

  **This will remove query parameters that exist today.** They still work and are marked deprecated in the [REST API](https://docs.bridge.new/api-reference/health/health-check.md) reference. The date they stop being accepted will be published here before that happens; the lookup endpoints that replace them are available now.

### What changes

**Available now:** `GET /contacts/lookup` and `GET /users/lookup` return one contact or one Bridge User (an internal user, in the API reference) by an identifier.

**Deprecated, to be removed:** the list endpoints will stop filtering. `GET /contacts` and `GET /users` will keep `limit` and `cursor` and nothing else.

| Deprecated | Replacement |
| ------- | ----------- |
| `GET /contacts?search=` — a cellphone | `GET /contacts/lookup?type=PHONE&value=…` |
| `GET /contacts?search=` — an email | `GET /contacts/lookup?type=EMAIL&value=…` |
| `GET /contacts?search=` — a name | **none** |
| `GET /contacts?ownerEmail=` | **none** |
| `GET /users?email=` | `GET /users/lookup?type=EMAIL&value=…` |
| `GET /users?status=` | **none** — every row already carries `status` |

Once removed, a parameter will be **refused**, not ignored. Sending one will return `400` with `BRIDGE_CORE_0103`, and the response will name the parameter. We chose this deliberately: a call that silently ignored your filter would hand you the first page of your whole workspace and let you treat it as a match.

### What to do

**If you search by cellphone or email**, move to the matching lookup endpoint. It answers with the same object the list returns for each row, and returns `404` when nothing matches.

`type` takes the identifier types the API already uses elsewhere — the same values as `identifierType` on a conversation participant. Contacts accept `ID`, `EMAIL` and `PHONE`; Bridge Users accept `ID` and `EMAIL`, since a Bridge User's cellphone is not an addressable identifier in Bridge.

`ID` is accepted for the same reason: code that already carries an `{identifierType, identifier}` pair should not have to branch on one of the values to build a different URL. It returns exactly what `GET /contacts/{contactId}` returns, and that remains the canonical URL for a contact — prefer it when the id is what you hold.

```bash
# Before
curl "https://api-connect-us.bridge.new/bridge/api/v1/workspaces/$WORKSPACE/contacts?search=%2B14084029292" \
  -H "x-api-key: $BRIDGE_API_KEY"

# After
curl "https://api-connect-us.bridge.new/bridge/api/v1/workspaces/$WORKSPACE/contacts/lookup?type=PHONE&value=%2B14084029292" \
  -H "x-api-key: $BRIDGE_API_KEY"
```

A `PHONE` is read the same way as the cellphone you send when you create a contact: a number without a country code is read in your workspace's default country, and spaces and separators are ignored. An `EMAIL` has its domain lowercased, but its local part is matched exactly as sent.

**Note**

  A cellphone in international form begins with `+`, which must be percent-encoded as `%2B` in a query string. Most HTTP clients do this for you when you pass parameters as a map rather than building the URL by hand.

A `value` that does not match its `type` — not a well-formed email, cellphone or UUID — is rejected with `422` and `BRIDGE_CORE_0101` before any lookup happens. Handle it separately from `404` if you pass user input straight through: one says *you sent something that is not an identifier*, the other says *nobody here holds it*.

**If you filter Bridge Users by status**, read `status` off each row instead. It is derived rather than stored, and it is already in every response. Note that today the list returns only active users unless you pass `status`; once the parameter is removed it will return active and disabled users alike.

The same applies to `GET /users/lookup`: it returns the Bridge User whether active or disabled, preferring the active one when an email matches both. `GET /users?email=` returns nothing for a disabled user today, so check `status` on the response if you only act on active users.

**If you search contacts by name**, there will be no replacement, and it is worth knowing what you would lose. The parameter only matches the **exact full name** — first name, one space, last name. It never matches a prefix, a partial, or a surname on its own. If it works for you, you are passing the complete name already.

**If you filter contacts by owner**, there will be no replacement. List the page and filter on `ownerId` in your own code. `ownerId` is the id of the owning Bridge User, not an email: get it once with `GET /users/lookup?type=EMAIL&value=…` and compare against its `id`.

### Why

Filtering on those parameters makes the cost of the call depend on the size of your workspace rather than the size of the answer. Looking up one contact by phone number in a large workspace reads tens of thousands of records to return one — and asking for a bigger page makes it slower, not faster. The lookup endpoints read only the records that hold that identifier.

This is also why the filters are being removed rather than fixed: where a replacement exists it is strictly better, and the name search, which has none, never matched anything but the exact full name.

# Receive Bridge webhooks

Source: https://docs.bridge.new/webhooks

Connect an HTTPS receiver to Bridge events and understand authentication, acknowledgement and asynchronous processing.

Webhooks send events **from Bridge to your system**. Configure an HTTPS callback and subscribe to the event families your integration needs. Bridge sends JSON using `POST`; your receiver authenticates and stores the event before returning `2xx`.

Use the [REST Integrations API](https://docs.bridge.new/credentials.md) when your system needs to read or change a Bridge resource. A webhook subscription does not create a complete two-way CRM integration by itself: your receiver must map identifiers, process the event and implement any intended write back through the documented REST operation.

## Build the receiver

  

### Choose your events

    Read the [event reference](https://docs.bridge.new/webhooks/events.md) and select the family and subscription version that matches your workflow.
  

  

### Verify and store each request

    Follow [Verify signatures](https://docs.bridge.new/webhooks/verifying-signatures.md) for the exact HMAC serialization and [Receive events](https://docs.bridge.new/webhooks/receive-events.md) for a durable inbox example.
  

  

### Configure and test the callback

    Enter the URL, webhook API key and client secret in the [Bridge Admin Console](https://docs.bridge.new/webhooks/configuration.md). Check the test callback before enabling your business workflow.
  

```mermaid
sequenceDiagram
    participant B as Bridge
    participant R as Your receiver
    participant I as Durable inbox
    participant W as Your worker
    B->>R: POST JSON event and authentication headers
    R->>R: Verify API key, HMAC and freshness policy
    R->>I: Commit verified event or confirm exact duplicate
    I-->>R: Durable acceptance
    R-->>B: 2xx acknowledgement
    W->>I: Read unprocessed events
    W->>W: Apply business action idempotently
```

## Keep the credentials separate

| Header | Purpose |
| --- | --- |
| `X-Bridge-API-Key` | Webhook API key configured for this callback. Compare it with your expected value. |
| `X-Bridge-Signature` | `sha256=` plus HMAC-SHA256 of Bridge's canonical event representation, using your webhook client secret. |
| `X-Bridge-Timestamp` | Unix seconds for a receiver freshness check. The HMAC does **not** include this header. |

These webhook credentials are separate from the REST API's `x-api-key` and the browser's Custom Connections `captureKey`. Keep the webhook client secret on your server.

## What an acknowledgement means

A `2xx` response means your receiver accepted the event. It does not establish that your CRM update or other business action completed. Persist first and process outside the request, so a slow downstream service does not hold up acknowledgement.

The current HTTP sender makes three attempts per delivery operation, with one- and two-second waits and a default ten-second socket timeout. This is not a promise of three attempts across the entire event pipeline. Read [retry, duplicate and ordering behavior](https://docs.bridge.new/webhooks/receive-events.md) before choosing your recovery policy.

Do not assume exactly-once delivery, a global event order, or a public replay endpoint. The [event reference](https://docs.bridge.new/webhooks/events.md) describes payloads; the [receiver guide](https://docs.bridge.new/webhooks/receive-events.md) explains how to handle them reliably.

# Verify webhook requests

Source: https://docs.bridge.new/webhooks/verifying-signatures

Verify the webhook API key and the exact HMAC representation used by Bridge, then deduplicate accepted events.

Verify each request before accepting it into your system. Use the **webhook** API key and client secret configured for this callback; these are separate from your REST Integrations API key.

## Authentication headers

| Header | Check |
| --- | --- |
| `X-Bridge-API-Key` | Constant-time comparison with the webhook API key you configured |
| `X-Bridge-Signature` | `sha256=` followed by the lowercase HMAC-SHA256 hex digest |
| `X-Bridge-Timestamp` | Unix seconds within your accepted freshness window; the example allows five minutes in either direction |

Header names are case-insensitive.

## Exactly what is signed

Bridge builds the HMAC input from the JSON event using the Python expression below, then encodes that string as UTF-8:

```python
json.dumps(event, sort_keys=True).encode("utf-8")
```

This sorts object keys recursively, preserves array order, escapes non-ASCII characters, and uses Python's default spaces after commas and colons. It does not append a newline. The key is the client secret encoded as UTF-8. This is a Python JSON serialization convention, not RFC 8785 / JCS.

Do not replace it with a digest of arbitrary raw request bytes, compact JSON, a generic JavaScript `JSON.stringify`, or a timestamp-prefixed string. Whitespace, Unicode escaping and number formatting can change the HMAC input even when the parsed object looks equivalent. Use the Python verifier below or test another implementation against the vector before connecting it.

**Warning**

  The current HMAC input contains the event JSON only. **`X-Bridge-Timestamp` is not included in the signature.** Check freshness, but do not treat the timestamp alone as cryptographic replay protection: a previously valid payload and signature can be presented with a different timestamp. Authenticate the webhook API key and use a durable inbox and idempotent business processing as described in [Receive events](https://docs.bridge.new/webhooks/receive-events.md).

## Python verifier

Save this as `bridge_webhooks.py`. It returns the verified parsed object so downstream code uses the same interpretation that was authenticated. Secrets should come from server-side environment variables or your secret store.

```python
import hashlib
import hmac
import json
import re
import sqlite3
import time


class VerificationError(ValueError):
    pass


def canonical_payload(event):
    # Match Bridge's Python json.dumps defaults: sort recursively, ASCII escapes,
    # a space after commas and colons, then UTF-8. This is not RFC 8785 / JCS.
    return json.dumps(event, sort_keys=True).encode("utf-8")


def _unique_object(pairs):
    result = {}
    for key, value in pairs:
        if key in result:
            raise VerificationError("Duplicate JSON object key")
        result[key] = value
    return result


def verify_webhook(raw_body, headers, webhook_api_key, client_secret, *, now=None, tolerance=300):
    headers = {key.lower(): value for key, value in headers.items()}
    received_key = headers.get("x-bridge-api-key", "")
    if not received_key or not webhook_api_key or not client_secret:
        raise VerificationError("Missing webhook credentials")
    if not hmac.compare_digest(received_key.encode("utf-8"), webhook_api_key.encode("utf-8")):
        raise VerificationError("Invalid webhook API key")

    received_signature = headers.get("x-bridge-signature", "")
    if not re.fullmatch(r"sha256=[0-9a-f]{64}", received_signature):
        raise VerificationError("Invalid signature format")
    timestamp = headers.get("x-bridge-timestamp", "")
    if not re.fullmatch(r"[0-9]+", timestamp):
        raise VerificationError("Invalid timestamp")
    current_time = time.time() if now is None else now
    if abs(current_time - int(timestamp)) > tolerance:
        raise VerificationError("Timestamp outside the permitted window")

    try:
        event = json.loads(raw_body.decode("utf-8"), object_pairs_hook=_unique_object)
    except (UnicodeDecodeError, json.JSONDecodeError) as exc:
        raise VerificationError("Invalid JSON body") from exc
    if not isinstance(event, dict):
        raise VerificationError("Expected a JSON object")
    expected = "sha256=" + hmac.new(
        client_secret.encode("utf-8"), canonical_payload(event), hashlib.sha256
    ).hexdigest()
    if not hmac.compare_digest(expected, received_signature):
        raise VerificationError("Invalid webhook signature")
    return event

```

The five-minute window is receiver policy; keep your server clock synchronized. The verifier also rejects ambiguous duplicate JSON keys. Do not disable authentication when debugging a mismatch: check the configured webhook credentials and compare the canonical input against the fixture below.

Changing a field must fail verification. Changing only input key order or sending literal Unicode instead of JSON Unicode escapes must still verify after parsing and rebuilding the same canonical representation.

## After verification

Commit the event to a durable inbox before acknowledging it. A valid HMAC confirms the authenticated event representation; it does not prove that your business action has run, that the event is new, or that it is the latest state of the resource. Continue with [delivery, duplicates and ordering](https://docs.bridge.new/webhooks/receive-events.md).

# Receive events reliably

Source: https://docs.bridge.new/webhooks/receive-events

Verify, persist and acknowledge webhooks, then process duplicates and out-of-order events safely.

A webhook receiver has two jobs: accept an authenticated event quickly, then process it reliably. Keep slow CRM calls, enrichment and other business work outside the HTTP request.

## Receive → verify → persist → acknowledge

1. Read the request body and headers.
2. Verify the webhook API key, canonical HMAC and timestamp policy with [the verifier](https://docs.bridge.new/webhooks/verifying-signatures.md).
3. Atomically store the verified event in a durable inbox, or confirm that this exact event is already there.
4. Return a `2xx` response promptly. Process stored events in a worker and make each business action idempotent.

Return success only after durable acceptance. If storage is unavailable, return a non-`2xx` response so the delivery attempt is not acknowledged. A duplicate that is already stored should receive `2xx` again.

## Retry behavior

The current sender makes up to **three HTTP attempts** for one delivery operation. It waits **one second**, then **two seconds**, before the remaining attempts. Any `2xx` response stops those attempts. A non-`2xx` response, a connection failure or a request exception can trigger the next attempt. The default socket timeout is **10 seconds** per attempt; acknowledge in a few seconds rather than relying on a 30-second allowance.

The payload, signature and timestamp headers are reused within that delivery operation. These three attempts are a bound for one send operation, **not an end-to-end ceiling on all deliveries of an event**. If an upstream event is delivered again, it can invoke the sender again. No total retry count or replay horizon is promised here. Do not rely on a `Retry-After` response header to set Bridge's retry timing.

If all attempts fail, the delivery is considered failed. Do not assume indefinite automatic retry or a public replay endpoint. For investigation, keep the event's workspace, type, ID and approximate time, and contact Bridge support. Do not include webhook credentials in support messages or application logs.

## Duplicates and event identity

Your service may have committed an event even when Bridge did not receive your `2xx` response. Retrying it must not create a second CRM update, invoice, message or other business effect.

Scope an inbox record to `workspaceId`, `eventType` and `eventId`. Also store a digest of the verified event. Do not assume `eventId` is a globally unique ID across every notification family: some notifications use an entity-derived ID. Retain distinct payloads that share an ID, then apply business idempotency for the operation your worker performs.

The example below deduplicates exact repeated events using all three identifiers plus the SHA-256 fingerprint of the canonical event. This is an inbox key for this example, not a new Bridge request field.

Do not expire a deduplication record merely because the five-minute timestamp window has passed. That header is not signed, so the window does not establish a safe replay expiry. Choose retention around your business reconciliation needs and keep destination-side business actions idempotent. The example does not automatically delete inbox records.

## Minimal durable receiver

Add these definitions to the `bridge_webhooks.py` module from [Verify webhook requests](https://docs.bridge.new/webhooks/verifying-signatures.md). The verifier module already includes the imports used below.

```python
class SQLiteInbox:
    """Single-service example inbox. Use a shared durable store for multiple replicas."""
    def __init__(self, path):
        self.path = str(path)
        with sqlite3.connect(self.path) as db:
            db.execute("""CREATE TABLE IF NOT EXISTS webhook_inbox (
                workspace_id TEXT NOT NULL, event_type TEXT NOT NULL,
                event_id TEXT NOT NULL, fingerprint TEXT NOT NULL,
                body TEXT NOT NULL, received_at REAL NOT NULL,
                processed INTEGER NOT NULL DEFAULT 0,
                PRIMARY KEY(workspace_id, event_type, event_id, fingerprint)
            )""")

    def accept(self, event):
        identifiers = [event.get(key) for key in ("workspaceId", "eventType", "eventId")]
        if not all(isinstance(value, str) and value for value in identifiers):
            raise VerificationError("Missing event envelope identifiers")
        body = canonical_payload(event)
        fingerprint = hashlib.sha256(body).hexdigest()
        with sqlite3.connect(self.path, timeout=3) as db:
            cursor = db.execute(
                """INSERT OR IGNORE INTO webhook_inbox
                (workspace_id, event_type, event_id, fingerprint, body, received_at)
                VALUES (?, ?, ?, ?, ?, ?)""",
                (*identifiers, fingerprint, body.decode("utf-8"), time.time()),
            )
            inserted = cursor.rowcount == 1
        # Context manager commits before the request can be acknowledged.
        return inserted


def make_wsgi_app(inbox, webhook_api_key, client_secret):
    """Verify, commit an inbox record, then acknowledge; workers process it later."""
    def app(environ, start_response):
        if environ.get("REQUEST_METHOD") != "POST":
            start_response("405 Method Not Allowed", [("Allow", "POST")])
            return [b""]
        try:
            length = int(environ.get("CONTENT_LENGTH") or "0")
            if length < 1:
                raise VerificationError("Missing JSON body")
            raw_body = environ["wsgi.input"].read(length)
            headers = {
                "x-bridge-api-key": environ.get("HTTP_X_BRIDGE_API_KEY", ""),
                "x-bridge-signature": environ.get("HTTP_X_BRIDGE_SIGNATURE", ""),
                "x-bridge-timestamp": environ.get("HTTP_X_BRIDGE_TIMESTAMP", ""),
            }
            event = verify_webhook(raw_body, headers, webhook_api_key, client_secret)
            inbox.accept(event)  # A duplicate exact event is also acknowledged.
        except (VerificationError, ValueError):
            status, body = "400 Bad Request", b'{"accepted":false}'
        except sqlite3.Error:
            status, body = "503 Service Unavailable", b'{"accepted":false}'
        else:
            status, body = "200 OK", b'{"accepted":true}'
        start_response(status, [("Content-Type", "application/json"), ("Content-Length", str(len(body)))])
        return [body]
    return app

```

Create the WSGI application in your server configuration:

```python
import os

from bridge_webhooks import SQLiteInbox, make_wsgi_app

application = make_wsgi_app(
    SQLiteInbox(os.environ["WEBHOOK_INBOX_PATH"]),
    os.environ["BRIDGE_WEBHOOK_API_KEY"],
    os.environ["BRIDGE_WEBHOOK_CLIENT_SECRET"],
)
```

Use a durable database path for this single-service example. When you run multiple receiver replicas, use a shared store with an equivalent atomic uniqueness constraint. Enforce your service's request-size and network policies at the HTTP server, and terminate HTTPS there.

This example stops at durable acceptance. A worker must read rows with `processed=0`, perform the business action idempotently, and mark them processed only after success. A local acknowledgement is not proof that the business action completed.

## Ordering and reconciliation

Do not rely on a global delivery order. Different resource families and independent delivery attempts can interleave. Route on the published `eventType` and use the schema for that subscription.

Where a payload includes `sequence`, treat it as a resource/stream ordering hint, not a global counter shared by all workspaces or event families. Do not invent it for events whose schema has no sequence. Preserve source timestamps and identifiers, and avoid replacing newer state with an older notification. Where the REST API supports reading the resource, fetch current state when an event leaves the result uncertain; otherwise use the event-family guidance or contact support.

Do not require a universal `version` field in every event envelope. For the supported event families in this webhook service, the configured subscription version selects that family's registered transformer and payload schema. Follow the documented schema for that family and subscription; do not infer a version property that its envelope does not publish.

## Check the receiver before launch

Verify the provided signature vector, a changed payload, a wrong API key, expired and future timestamps, duplicate delivery after a process restart, storage failure, and two distinct payloads sharing an ID. A re-timestamped replay of a previously signed payload demonstrates why the durable inbox is needed in addition to the timestamp check.

Use Bridge's console test webhook to validate the connection and configured credentials after deploying your receiver. A successful test demonstrates the callback path; it does not establish delivery or ordering guarantees for every business event.

## Call Notifications

v1

Triggered as a call moves through its lifecycle. Bridge emits at most one webhook per lifecycle phase per call, so your integration receives a clean four-phase timeline (created, ringing, started, finished) rather than every intermediate state transition Bridge writes internally.

The current phase is derivable from the call state and the participants' statuses:

| Phase    | How to detect                                                            |
| -------- | ------------------------------------------------------------------------ |
| created  | state is CREATED and no participant has joined or is ringing             |
| ringing  | a participant has status RINGING and nobody has joined yet               |
| started  | state is STARTED and two participants are JOINED                         |
| finished | state is FINISHED                                                        |

Missed calls (nobody answered) skip the started phase — the integration receives created, ringing, and finished only.

Once a call finishes, Bridge runs the recording through an asynchronous AI transcription pipeline. When the transcript is ready, the integration receives an additional `call.transcription.created` event with the full transcript broken down into time-coded segments per speaker. This event arrives **after** the `call.updated (finished)` event, typically several seconds to a few minutes later depending on call length. Diarization (multi-speaker labelling) depends on the audio source quality — mono recordings may produce a single speaker label for the entire transcript.

  

### Event types

    | Event Type                    | Description                                                 |
    | ----------------------------- | ----------------------------------------------------------- |
    | `call.created`                | A new call was provisioned                                  |
    | `call.updated`                | A call lifecycle phase changed (ringing, started, finished) |
    | `call.transcription.created`  | The AI transcript for a finished call is ready              |

# Custom Connections

Source: https://docs.bridge.new/lead-capture/index

Use Custom Connections to register leads from your landing page and queue an opening WhatsApp message.

## What this does

Your landing page posts a lead to Bridge. Bridge then opens the WhatsApp conversation for
you, using an approved template. You do not send the message; we do.

**Warning**

  **A `202` response means the lead was accepted, not that a message was sent.** The first
  WhatsApp message is transmitted later by a separate service. Your thank-you copy must say
  something like "we'll message you shortly" — never "we've messaged you".

## What you need, and where it comes from

Four values: the endpoint URL, your `captureKey`, the reCAPTCHA site key, and the reCAPTCHA
action name.

You do not assemble them by hand. In the Bridge admin console, under **LeadScout → Capture
snippet**, an administrator of your workspace generates an integration example that already
contains all four. They hand that block to whoever builds the page — that person never needs
console access.

**Note**

  The example is a starting point, not a drop-in script. You own your form markup and your
  consent wording; see [Consent requirements](https://docs.bridge.new/lead-capture/consent.md).

# Consent requirements

Source: https://docs.bridge.new/lead-capture/consent

What your opt-in must say, and what you are attesting to when you send consent.status GRANTED.

## What your form must carry

Your landing page must ask for an explicit opt-in before you submit a lead. The wording is
yours to write, but it has to do two things Meta requires:

- **Name your business.** Not "us", not "our partners" — the business the person will hear
  from.
- **Say the person will receive WhatsApp communication from it.** Not "we may contact you";
  name the channel.

Meta lists a website form as a compliant way to collect this, so a checkbox on your landing
page is enough — provided it says both of those things.

**Warning**

  A pre-ticked box is not an opt-in. Neither is a line of small print under a submit button
  that the visitor never interacts with. The visitor has to take the action.

## What you are attesting to

**Note**

  Sending `consent.status: "GRANTED"` is an attestation **you** are making. We do not and
  cannot verify that the visitor ticked a box — we record that you told us they did, and
  when. If your WhatsApp sending is ever restricted, that record is what is presented on
  your behalf.

This is why `capturedAt` matters more than it looks. It must be the moment the visitor
actually consented — not the moment your server got around to sending the request, and not a
timestamp generated during a nightly batch. If the two ever have to be defended, the gap
between them is the first thing anyone will look at.

Send it as an ISO 8601 timestamp:

```json
{
  "consent": {
    "status": "GRANTED",
    "capturedAt": "2026-08-26T14:32:07.184Z"
  }
}
```

If consent was not given, do not submit the lead. A submission with any status other than
`GRANTED` is rejected with `BRIDGE.CAMPAIGN_LEADS.CONSENT_NOT_GRANTED`.

## An example to adapt

This is illustrative, not boilerplate to paste. Only you know what you will send and why,
and the wording has to match that.

> ☐ I agree to receive WhatsApp messages from **Acme Motors** about the quote I just
> requested.

What makes it work: it names the business, it names the channel, and it says what the
messages will be about. What would break it: dropping the business name, saying "messages"
without saying WhatsApp, or bundling the consent into a general terms-and-conditions
checkbox that also covers unrelated things.

# Template requirements

Source: https://docs.bridge.new/lead-capture/templates

Supported template categories and guidelines for opening conversations through Custom Connections.

## Supported template categories

The template that opens the conversation can be either a **utility** or a **marketing** template:

- **Utility templates**: Strictly transactional, echoing what the visitor just submitted (such as confirming receipt of an enquiry). These qualify for lower WhatsApp conversation rates.
- **Marketing templates**: May include promotional language, discounts, special offers, or direct sales pitches. These are billed at standard WhatsApp marketing conversation rates.

**Note**

  **Authentication** templates cannot be used with Custom Connections. Any template configured with the `AUTHENTICATION` category will be rejected.

You configure and submit your templates directly in Meta WhatsApp Manager, and getting them approved is a prerequisite for going live.

## Meta classification and deliverability

**Warning**

  Meta classifies templates by their content, not strictly by the category you select during submission. If a template submitted as UTILITY contains promotional language, Meta may reclassify it as MARKETING or reject it.

Choosing the right category upfront prevents unintended classification issues and ensures expected deliverability and billing.

## Category examples

**Utility (Transactional)** — acknowledges an enquiry without promotional offers:

```text
Hi {{1}}, thanks for your enquiry about the {{2}}. A member of our team will follow up here shortly.
```

**Marketing (Promotional)** — includes promotional language, discounts, or sales offers:

```text
Hi {{1}}, thanks for your enquiry about the {{2}}. Book this week and get 15% off — reply YES to claim.
```

## Practical guidance

- **Choose Utility** when your primary goal is rapid transactional follow-up confirming the visitor's request. Keep it strictly focused on echoing their submission without promotional hooks to maintain the utility category and lower messaging rate.
- **Choose Marketing** when you want to immediately provide introductory discounts, promotional incentives, or catalog offers upon capture.
- **Avoid Authentication templates**: Authentication templates are intended exclusively for one-time passwords and verification codes, and are rejected for campaign lead dispatches.
- Once the person replies, you are in a normal conversation session and template category constraints no longer apply to incoming or agent responses.

  was accepted and queued -- a separate service sends the first WhatsApp message later, so
  do not tell the visitor "message sent"; something like "we'll message you shortly" is
  accurate.
-->

    "use strict";
    var form = document.getElementById("lead-form");
    var consentBox = document.getElementById("lead-consent");
    var submitButton = form.querySelector("button[type=submit]");
    var result = document.getElementById("lead-result");

    var inFlight = false;
    var accepted = false;
    var submissionStarted = false;
    var responseReceived = false;
    consentBox.addEventListener("change", function () {
      consentCapturedAt = consentBox.checked ? new Date().toISOString() : null;
    });
    function showResult(message) {
      result.textContent = message;
    }
    function loadRecaptcha() {
      return new Promise(function (resolve, reject) {
        if (window.grecaptcha) {
          resolve();
          return;
        }
        var tag = document.createElement("script");
        tag.src = "https://www.google.com/recaptcha/api.js?render=" + config.recaptchaSiteKey;
        tag.onload = function () {
          resolve();
        };
        tag.onerror = function () {
          reject(new Error("Could not load reCAPTCHA. Check the site key and the network."));
        };
        document.head.appendChild(tag);
      });
    }
    // Mint the token on submit, not on page load: a reCAPTCHA v3 token is only valid for
    // ~2 minutes, so minting it earlier means it can already be expired by the time the
    // visitor actually submits the form.
    function mintToken() {
      return loadRecaptcha().then(function () {
        return new Promise(function (resolve, reject) {
          window.grecaptcha.ready(function () {
            window.grecaptcha
              .execute(config.recaptchaSiteKey, { action: config.recaptchaAction })
              .then(resolve, reject);
          });
        });
      });
    }

    // trackedParams are collected. The rest of the query string can carry ad-network
    // click ids or session tokens that were never meant to be stored -- over-collection
    // here is irreversible, so when in doubt leave a param out.
    function readCampaignParams() {
      var params = new URLSearchParams(window.location.search);
      var collected = {};
      params.forEach(function (value, key) {
        if (key.indexOf("utm_") === 0 || config.trackedParams.indexOf(key) !== -1) {
          collected[key] = value;
        }
      });
      return collected;

        captureKey: config.captureKey,

        name: document.getElementById("lead-name").value.trim() || null,

            showResult("We could not confirm whether your request was accepted. Check with the business before submitting it again.");
            return;
          }
          showResult(error.message || "The request could not be completed.");
        })
        .finally(function () {
          inFlight = false;
          submitButton.disabled = accepted;
        });

## What the example does

- Checks the form's required fields before obtaining a CAPTCHA token.
- Records `consent.capturedAt` when the visitor selects the checkbox. If the browser restores an old checked state, it asks for a fresh consent action.
- Allows one submission at a time and keeps the button disabled after acceptance to avoid another submission from this form instance.
- Shows a `202` as accepted and queued, and displays the returned `requestId` as a support reference. It never says a WhatsApp message was delivered.
- Shows recoverable CAPTCHA failures and creates a fresh token on each manual attempt. It does not retry a POST automatically.
- Treats a network failure after submission as an uncertain outcome; it does not claim that the lead was rejected or safe to resend.

This is client-side feedback, not a backend deduplication guarantee. Adapt the visible messages to your page and retain the [error reference](https://docs.bridge.new/lead-capture/errors.md) for diagnosis.

## Your capture key is not an API key

**Note**

  If you have read the [Authentication](https://docs.bridge.new/credentials.md) page, it tells you never to put a key
  in frontend code. That rule is about the Integrations API key, and it still holds. Your
  `captureKey` is a different kind of value.

Unlike the `x-api-key` used by the Integrations API, your `captureKey` is designed to live
in your page's HTML where anyone can read it. It grants no read access to anything: it only
identifies which workspace a submission belongs to. Abuse is bounded by two other checks —
the reCAPTCHA token, and the fact that submissions are only accepted from the domains
registered for your workspace.

Never use your Integrations API key here, and never put one in a page.

## Put the workspace id on the URL

The workspace id goes in the request body **and** on the URL as `?workspaceId=...`. It has
to be in both places: a browser sends a CORS preflight before the real request, and that
preflight carries no body — so without the id on the URL we cannot tell which workspace you
are, cannot return the header that authorises your domain, and the browser blocks the
request before it is ever sent.

The failure this causes is confusing, which is why it is worth getting right the first
time: you will see a CORS error in the browser console and no request in our logs at all,
because the real request never left the page.

## Mint the captcha token when the form is submitted

A reCAPTCHA v3 token is valid for about two minutes. Minting it when the page loads means
it is often already expired by the time somebody finishes typing, and it comes back
rejected — as a `403`, which looks like a permissions problem rather than a timing one.

## Mint a new token for every attempt

A token verifies exactly once. If a submission fails and you retry with the same token, the
replay is indistinguishable from an attack and returns the same error a bot would get.
Always call `grecaptcha.execute` again before retrying.

## What to send

The [endpoint reference](https://docs.bridge.new/api-reference/campaign-leads/register-a-campaign-lead.md) carries the full contract.
These are the fields whose meaning is not obvious from the schema alone:

### `brandId` (`string`)

  The brand your landing page sells — not a line, channel or phone number id. Required only
  if your workspace has brands enabled. **A line id is never required.**

### `landingUri` (`string`)

  The page's origin and path, without the query string. Your UTMs travel separately in
  `utm`, and a raw query string often carries click ids or session tokens that should not be
  stored. Send `https://example.com/offer`, not `https://example.com/offer?gclid=...`.

### `consent` (`object`)

  Your attestation that the visitor opted in, and when. See
  [Consent requirements](https://docs.bridge.new/lead-capture/consent.md) — the wording on your form is not optional.

### `utm` (`object`)

  Collected from the query string against an allowlist: `utm_*` parameters plus any extra
  names you configure in the console. This is an allowlist rather than a denylist on
  purpose — over-collecting here is not reversible.

## After you submit

A `202` means the lead was accepted and queued. It does **not** mean a message was sent —
that happens later, in a separate service. Tell the visitor you will message them shortly.

Anything else is an error. See the [error reference](https://docs.bridge.new/lead-capture/errors.md) for what each one
means and whether it is yours to fix.

# Error reference

Source: https://docs.bridge.new/lead-capture/errors

Every response the Custom Connections endpoint can return, and whether you can fix it.

Error responses are [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem details: a
`type`, a `title`, a `status`, and sometimes a `detail`.

**Note**

  **Error responses do not carry a request id.** Only a successful `202` does. If you need
  to raise something with support, report the page URL and the approximate time instead.

## Every response

| Status | `type` | What happened | Can you fix it? |
| --- | --- | --- | --- |
| `400` | `invalid_payload` | A field is missing or malformed. | Yes |
| `400` | `BRIDGE.CAMPAIGN_LEADS.INVALID_PHONE` | The phone number could not be read as a real number. | Yes — validate before submitting |
| `400` | `BRIDGE.CAMPAIGN_LEADS.CONSENT_NOT_GRANTED` | `consent.status` was not `GRANTED`. | Yes |
| `400` | `BRIDGE.CAMPAIGN_LEADS.BRAND_OR_LINE_REQUIRED` | Your workspace has brands enabled and no `brandId` was sent. | Yes |
| `403` | `BRIDGE.CAMPAIGN_LEADS.CAPTURE_DISABLED` | The Custom Connections feature is not enabled for this workspace. | No — contact Bridge |
| `403` | `BRIDGE.CAMPAIGN_LEADS.CAPTURE_KEY_MISMATCH` | The capture key is missing or wrong. | Yes |
| `403` | `BRIDGE.CAMPAIGN_LEADS.CAPTCHA_REJECTED` | The captcha token was missing, expired, already used, or scored too low. | Sometimes — see below |
| `403` | `BRIDGE.CAMPAIGN_LEADS.ORIGIN_NOT_ALLOWED` | The page's domain is not registered for this workspace. | No — contact Bridge |
| `422` | `BRIDGE.CAMPAIGN_LEADS.CAPTCHA_PROVIDER_UNAVAILABLE` | We could not reach the captcha provider. | Retrying is safe |
| `500` | `unexpected_error` | Something failed on our side. | No |

Only the first failure is reported. Checks run in this order: workspace and capture key,
then the phone number, then consent, then the brand, then the captcha and finally the
domain. Fixing one error can reveal the next.

## About the captcha rejection

`CAPTCHA_REJECTED` covers four different situations. Check the token handling in your integration before attributing a rejection to the score:

- **The token expired.** It was minted too early. A reCAPTCHA v3 token lasts about two
  minutes; mint it when the form is submitted, not when the page loads.
- **The token was already used.** A token verifies once. If you retried a failed submission
  without minting a new token, the replay is rejected.
- **No token was sent.** Make sure your client obtains a token and includes it in `recaptchaToken` on every submission.
- **The score was too low.** The anti-bot check rejected this attempt. Do not bypass it.

All four situations return the same code, so the response alone does not identify the cause. First check that the token is present, minted on submit, and fresh for every attempt.

## About the 422

This is a transient failure on our side: we could not reach the captcha provider, so we
could not decide whether the submission was genuine.

**Retrying is safe.** The lead is preserved when this happens, and a retry cannot produce a
duplicate message. Mint a fresh captcha token for the retry, as you would for any other one.

## About the domain error

The ordering here is genuinely surprising, so it is worth stating plainly.

Your page's domain is checked against the domains registered for your workspace — but the
domain we check is the one the **captcha provider reports**, not the one in the request's
own headers. That check happens *after* the token verifies.

The practical consequence: a page served from an unregistered domain fails at the captcha
stage with `ORIGIN_NOT_ALLOWED`, not with a CORS error. If you are seeing this while your
integration otherwise works, the domain is missing from your workspace configuration —
contact Bridge to have it added.

# Initiate a leadscout outbound conversation with a known lead

Source: https://docs.bridge.new/api-reference/leadscout-api/initiate-a-leadscout-outbound-conversation-with-a-known-lead

**Operation reference:** `post /bridge/api/v1/workspaces/{workspaceId}/leadscout/outbound`

**operationId:** `initiate_leadscout_outbound_bridge_api_v1_workspaces__workspaceId__leadscout_outbound_post`

Start a LeadScout outbound conversation with a known Contact. The Contact must already exist. Bridge resolves a prospecting Agent for an eligible WhatsApp line. The template is referenced by template.id or template.name; the id wins when both are supplied. It must exist and be APPROVED, and any handoffOverride Bridge User must be valid.

An explicit contact.providerChannelId is respected. Without one, automatic selection prefers a free line, then a released recoverable conversation with this Contact, then an occupied active conversation only when forceSend=true. Availability is per Contact on each line, not global line occupancy.

forceSend=true reuses an eligible active conversation; it does not ignore it or create a fresh one. A successful reuse returns alreadyInitiated=true and persists the new template and follow-ups. A recoverable released conversation can be recovered with either value, retains its ID, and returns recovered=true. Blocked and released nonrecoverable conversations are not made usable by this flag. The legacy route can reuse a conversation held by a human or another Agent; unlike Agents outbound, it does not enforce the requested-Agent controller check.

A nonexpired open LeadScout session still blocks a new outbound request with 409 BRIDGE_AI_LEADSCOUT_0017; inability to finalize an expired session returns 409 BRIDGE_AI_LEADSCOUT_0018. Other validation still applies. Additional messages are persisted; persistence does not prove delivery or a wait for the lead to reply. A failed request can leave partial work, so do not treat forceSend as idempotency or blindly retry an uncertain result.

See [the complete outbound guide](https://docs.bridge.new/guides/agent-outbound.md) for the false/true matrix, response flags, differences from Agents outbound, errors and handoff.

Return a template's variables — agnostic `key`/`label`/`callerMustSupply`/`isCustom`/`default`.

# Start an outbound conversation with a contact as a given agent

Source: https://docs.bridge.new/api-reference/agents-api/start-an-outbound-conversation-with-a-contact-as-a-given-agent

**Operation reference:** `post /bridge/api/v1/workspaces/{workspaceId}/agents/{agentId}/outbound`

**operationId:** `start_agent_outbound_bridge_api_v1_workspaces__workspaceId__agents__agentId__outbound_post`

Start an outbound conversation with a known Contact, answered by the given Agent.

Works for LeadScout and Service Agents. The Contact is resolved first, then the Agent, which must exist in
the workspace and be available (see `GET /agents`). The template is referenced by `template.id` or
`template.name` (the id wins when both are sent), must exist and be APPROVED, and a
`handoffOverride` Bridge User must be valid. If `template.media.mediaId` is unknown, the request fails
with 400 `BRIDGE_AI_LEADSCOUT_0016` only after the conversation was created or recovered, so a retry after
that error may answer differently. Body rules (`consent.status=GRANTED` without `capturedAt`, `template.media`
without exactly one of `mediaId` or `url`) fail with 400 `BRIDGE_CORE_0103`.

The conversation opens on one of the Agent's active WhatsApp lines, controlled by the Agent, with the template
as its first message. A line is picked in this order:
- A free line.
- Otherwise, a line holding a released conversation with this Contact that can be recovered. Recovering
  returns `recovered=true` and replaces the previous outbound context and `agentContext`. This happens even
  with `forceSend=false`.
- Otherwise, when no line is free or recoverable: `forceSend=false` (default) fails with 409
  `BRIDGE_AI_LEADSCOUT_0008`; `forceSend=true` reuses a line occupied by an active conversation with this
  Contact, preferring one this Agent controls. If the chosen conversation is held by another Agent or a
  Bridge User, the call fails with 409 `BRIDGE_AI_AGENT_OUTBOUND_0006` and nothing is written. Release it
  first, then retry. Lines whose conversation is blocked or was released without recovery are never used, so
  if no line is occupied by an active conversation the call fails with 409 `BRIDGE_AI_LEADSCOUT_0008` even
  with `forceSend=true`.

`contact.providerChannelId` is a preference: the pinned line is used when it is free or recoverable;
otherwise the same order applies over all the Agent's lines. Among occupied lines, one this Agent controls
comes first; if none does, the pinned line is the one reused (and may fail with 0006).

Reusing a conversation depends on the Agent type:
- LeadScout: if its LeadScout session is still open and not expired, the call fails with 409
  `BRIDGE_AI_LEADSCOUT_0017` (`extra` carries `conversationId`, `sessionId` and `stage`). If an expired
  session cannot be finalized, it fails with 409 `BRIDGE_AI_LEADSCOUT_0018`.
- Service Agent: an open, unexpired service session is continued; an expired one is closed as abandoned and a
  new one opens.

See [the complete outbound guide](https://docs.bridge.new/guides/agent-outbound.md) for prerequisites, the forceSend decision table, recovery, partial work and safe retry decisions.
